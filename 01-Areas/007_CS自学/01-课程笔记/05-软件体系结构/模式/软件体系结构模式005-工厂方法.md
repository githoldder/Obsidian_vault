# 工厂方法模式（Factory Method Pattern）

## 📖 问题-答案 / 步骤指导

### 工厂方法模式解决什么问题？

在软件系统中，经常面临"**一个类无法预先知道它所需创建对象的类型**"的问题。比如框架类 `Application` 需要创建 `Document`，但它不知道用户会创建文本文档还是电子表格还是 PDF。

**直接 new 的问题**：
```java
class Application {
    Document createDocument() {
        return new TextDocument();  // 硬编码！无法扩展
    }
}
```

如果用户需要创建 `SpreadsheetDocument`？改代码。需要创建 `PDFDocument`？再改。这违背了开闭原则——对修改封闭才是好设计。

**工厂方法模式的解决方案**：将**创建对象的操作延迟到子类中**。父类定义创建接口（抽象方法），子类重写该方法以生成具体对象。

### 工厂方法的四个角色

1. **Product（产品）**：定义工厂方法所创建对象的接口 —— `Document`
2. **ConcreteProduct（具体产品）**：实现 Product 接口 —— `TextDocument`、`SpreadsheetDocument`
3. **Creator（创建者）**：声明工厂方法（返回 Product），可能包含依赖 Product 的业务逻辑 —— `Application`
4. **ConcreteCreator（具体创建者）**：重写工厂方法，返回一个 ConcreteProduct 实例 —— `TextApplication`、`SpreadsheetApplication`

### 标准工厂方法的实现步骤

**Step 1：定义产品接口**
```java
interface Document {
    void open();
    void save();
    void close();
}
```

**Step 2：实现具体产品**
```java
class TextDocument implements Document {
    public void open() { System.out.println("Opening text document..."); }
    public void save() { System.out.println("Saving text document..."); }
    public void close() { System.out.println("Closing text document..."); }
}

class SpreadsheetDocument implements Document {
    public void open() { System.out.println("Opening spreadsheet..."); }
    public void save() { System.out.println("Saving spreadsheet..."); }
    public void close() { System.out.println("Closing spreadsheet..."); }
}
```

**Step 3：定义抽象创建者 + 工厂方法**
```java
abstract class Application {
    // 核心业务逻辑——使用产品但不依赖具体产品
    public void newDocument() {
        Document doc = createDocument();  // 工厂方法
        doc.open();
        doc.save();
        doc.close();
    }
    
    // 工厂方法——子类决定具体产品
    protected abstract Document createDocument();
}
```

**Step 4：实现具体创建者**
```java
class TextApplication extends Application {
    @Override
    protected Document createDocument() {
        return new TextDocument();  // 子类决定创建什么
    }
}

class SpreadsheetApplication extends Application {
    @Override
    protected Document createDocument() {
        return new SpreadsheetDocument();
    }
}
```

**Step 5：客户端使用**
```java
Application app = new TextApplication();
app.newDocument();  // 创建文本文档
```

### 模板方法与工厂方法的协同

注意 `Application.newDocument()` 的实现模式：

```java
public void newDocument() {
    Document doc = createDocument();  // ← 工厂方法（可变步骤）
    doc.open();                       // ← 固定步骤
    doc.save();                       // ← 固定步骤
    doc.close();                      // ← 固定步骤
}
```

这正是**模板方法模式**——父类定义算法骨架（固定的步骤序列），子类实现可变步骤（创建哪种文档）。工厂方法常作为模板方法中的"钩子"使用，二者配合天衣无缝。

### 参数化工厂方法

工厂方法也可以接受参数来让一个具体创建者创建多种产品：

```java
abstract class Application {
    protected abstract Document createDocument(String type);
    
    public void newDocument(String type) {
        Document doc = createDocument(type);
        doc.open();
        doc.save();
        // ...
    }
}

class OfficeApplication extends Application {
    @Override
    protected Document createDocument(String type) {
        return switch (type) {
            case "text" -> new TextDocument();
            case "sheet" -> new SpreadsheetDocument();
            default -> throw new IllegalArgumentException(type);
        };
    }
}
```

这本质上是**工厂方法 + 简单工厂的混合体**。符合开闭原则吗？微妙的边界——增加新产品类型仍需改 switch，但框架本身的骨架仍然封闭。

### 工厂方法 vs 简单工厂

| 维度 | 简单工厂 | 工厂方法 |
|------|----------|----------|
| 扩展方式 | 修改工厂类 | 新增子类 |
| OCP 符合度 | 弱（改现有代码） | 强（不改已有代码） |
| 类数量 | 少 | 多（每个产品一个创建者子类） |
| 适用场景 | 产品类型少且稳定 | 产品类型多变化频繁 |
| GoF 模式？ | ❌（只是编程习惯） | ✅（正式模式） |

**实用建议**：如果你只有 3-5 种产品且未来不太可能增加，简单工厂完全够用。过度使用工厂方法只会让项目中多出一堆没什么用的 `XXXFactory` 子类。

### 工厂方法在 JDK 中的体现

Java 标准库中就藏着工厂方法：
- `java.util.Calendar.getInstance()` → 根据 Locale 返回 GregorianCalendar 或 BuddhistCalendar
- `java.text.NumberFormat.getInstance()` → 根据 Locale 返回不同数字格式化器
- `java.net.URLStreamHandlerFactory.createURLStreamHandler()` → 根据协议创建不同处理器

这些 API 的共同特征：**你不知道也不需要知道具体返回的类是哪个**，只知道它符合接口约定。这正是工厂方法的价值——封装不确定性，提供稳定的接口契约。

### 名言加持

> "Define an interface for creating an object, but let subclasses decide which class to instantiate." —— GoF

工厂方法模式的精髓不在"工厂"二字，在"子类决定"这个动作。它是**继承**和**多态**在创建对象场景下的一次完美配合，也是理解框架设计（框架调用你的代码，而非你调用框架的代码）的最佳实例。
