# 依赖倒置原则（DIP / Dependency Inversion Principle）

## 📖 定义-解释-示例

### DIP 的经典定义

> **高层模块不应该依赖低层模块，两者都应该依赖其抽象。抽象不应该依赖细节，细节应该依赖抽象。**
> —— Robert C. Martin

在传统结构化设计中，高层模块直接调用低层模块——这形成了"自顶向下"的依赖金字塔。DIP 反转了这个关系：高层模块和低层模块都依赖同一个**抽象接口**，而不是彼此直接依赖。这就是"倒置"的含义——不是依赖关系物理倒过来（高层不依赖低层，低层反过来也不依赖高层），而是**双方都转而依赖抽象**。

### 传统依赖 vs 依赖倒置——典型案例

**违背 DIP 的设计**：

```java
// 高层模块：用户注册服务
class UserService {
    private MySQLDatabase db = new MySQLDatabase();  // 直接依赖低层模块
    
    public void register(String username, String password) {
        db.insert("INSERT INTO users VALUES (?, ?)", username, password);
        // ...
    }
}

// 低层模块：MySQL 数据库操作
class MySQLDatabase {
    public void insert(String sql, Object... params) { ... }
}
```

**问题**：`UserService` 直接依赖 `MySQLDatabase` 这个具体类。未来想换成 PostgreSQL？或者写单元测试时需要 mock 数据库？对不起，整个 `UserService` 都要改。高层模块的业务逻辑和底层的数据存储实现死死耦合在一起。

**遵循 DIP 的设计**：

```java
// 抽象——双方都依赖它
interface Database {
    void save(String query, Object... params);
}

// 高层模块——依赖抽象
class UserService {
    private Database db;  // 依赖接口，不是具体实现
    
    public UserService(Database db) {  // 通过构造函数注入
        this.db = db;
    }
    
    public void register(String username, String password) {
        db.save("INSERT INTO users VALUES (?, ?)", username, password);
    }
}

// 低层模块——实现抽象
class MySQLDatabase implements Database {
    public void save(String query, Object... params) { /* MySQL实现 */ }
}

class PostgreSQLDatabase implements Database {
    public void save(String query, Object... params) { /* PostgreSQL实现 */ }
}

// 单元测试的 mock
class MockDatabase implements Database {
    public void save(String query, Object... params) { /* 测试存根 */ }
}
```

现在换数据库？创建新的 `PostgreSQLDatabase` 实现 `Database` 接口，注入给 `UserService` 即可。`UserService` 一行不改。这就是 DIP 的威力——**具体实现成为可替换的插件**。

### 为什么叫"倒置"？

传统思维中，"高层模块"调用"低层模块"，依赖箭头：`UserService → MySQLDatabase`。DIP 做了这样的事：

```
传统依赖：      UserService → MySQLDatabase

依赖倒置后：    UserService → Database ← MySQLDatabase
                                   ← PostgreSQLDatabase
                                   ← MockDatabase
```

高层的"拥有权"被倒置了——定义"Database 应该做什么"的接口现在由高层提出（"我需要 save 方法"），低层只是这个契约的一个具体实现。

### DIP 与依赖注入（DI）

**DIP ≠ DI**。很多人把它们搞混：

- **依赖倒置（DIP）**：原则——**你应该依赖抽象而不是具体**
- **依赖注入（DI）**：实现技术——**通过外部控制将实现注入进来**（构造函数注入、Setter 注入、接口注入）
- **控制反转（IoC）**：DI 的更高层概念——**对象的创建和生命周期管理权从使用者手中转移到外部容器**

三者关系：IoC 容器通过 DI 实现，DI 是 DIP 的一种具体实现方式。你可以手动 DI（new 一个 MySQLDatabase 传给 UserService 的构造函数），也可以用 Spring/Guice 等 IoC 容器自动管理。

### DIP 的实践指南

**依赖什么样的抽象？**
抽象应该由**高层模块定义**，因为高层模块最清楚自己需要什么。`UserService` 定义 `Database` 接口，数据库实现适配这个接口——这叫"接口属于客户"原则。

**什么情况下不需要倒置？**
- **稳定模块**：`String`、`ArrayList` 这些 JDK 标准库基本不可能换，依赖它们不用倒置
- **不稳定的具体类**：你写的业务代码中的具体实现类（哪天换数据库、换消息队列、换支付渠道）——必须依赖它们的抽象版本

**判断标准**：如果一个具体类**可能变化**，就让它依赖抽象。`MySQL → PostgreSQL` 会变化 → 需要抽象。`String.length()` 永远不会变 → 不需要抽象。

### DIP 的常见反模式

**1. 抽象泄漏**
虽然声明依赖了接口 `Database`，但在使用处偷偷做了 instanceof 检查然后转型：
```java
if (db instanceof MySQLDatabase) {
    ((MySQLDatabase) db).mysqlSpecificFeature();
}
```
这个接口形同虚设——你本质上仍然依赖了具体实现。

**2. 过度抽象**
为不可变的工具类也创建抽象接口，增加无意义复杂度。如果只有一种数据库，且确定未来 5 年不会换，那就别为它写接口。

**3. 接口定义权在低层**
低层模块根据自己的实现细节定义了接口，高层被迫适配。正确的做法是高层定义接口、低层实现。因为高层最清楚"我需要什么"。

### 为什么 DIP 是 SOLID 的核心？

DIP 连接了 SRP（每个类独立于变化 → 具体实现与高层策略分离）和 OCP（依赖抽象后，替换实现不需要修改高层代码）。它是实现"对扩展开放、对修改关闭"的技术基础。
