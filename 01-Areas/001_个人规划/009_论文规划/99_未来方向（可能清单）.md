**人机协作的认知分工模型**。

你这句话尤其关键：

> **解决问题的过程，就是构建问题树本身，并逐一解决真正影响结果的问题的过程。**

我会稍微改一个词：

> **解决复杂问题 = 构建问题树 → 定位关键节点 → 将关键节点转化为可解问题 → 求解 → 根据结果重新修正问题树。**

因为真实工程里，问题树不是一次构建完成的，它会随着求解结果不断更新。

## 1. 你的核心思想可以压缩成一个公式

我建议把它抽象成：

$$
\boxed{ Problem\ Solving = Problem\ Construction + Problem\ Transformation + Problem\ Solving }
$$
而在人机协作环境下：
$$
\boxed{ Human:\ Why + How\ Else \qquad AI:\ How }
$$
当然这不是说 AI 不能做 Why，而是：

> **人的稀缺资源应该优先投入到 AI 最容易出错、但对整个问题结构影响最大的地方。**

这和“人负责思考，AI负责执行”又不完全一样。

更准确的是：

```text
Human
│
├── Why：真正的问题是什么？
│
├── Where：问题树中哪个节点真正影响结果？
│
├── How Else：这个问题能否转化成更适合 AI 求解的问题？
│
└── Boundary：什么时候应该停止 / 转向 / 重构？
│
▼
AI
│
├── Generate
├── Search
├── Implement
├── Calculate
├── Test
└── Iterate
```

所以你说的 **“问题在哪里，注意力就应该在哪里”**，我认为可以成为这个模型的第一原则。

# 2. 为什么这比“人负责需求，AI负责编码”更深一层？

传统 AI 编程经常是：

```text
人
↓
需求
↓
Prompt
↓
AI
↓
代码
↓
失败
↓
继续 Prompt
↓
继续失败
```

这里有一个隐含问题：

> **人默认接受了 AI 当前看到的问题定义。**

但真正困难的问题经常不是：

> “这个问题怎么解决？”

而是：

> **“我们现在解决的问题是不是正确的问题？”**

例如：

```text
用户说：
“网页太慢”

           ↓

AI：
“优化 React 渲染”

           ↓

实际上：
数据库查询 N+1
```

AI可能可以非常高效地解决：

> React 渲染优化

但这恰恰是**错误问题的高效解决**。

于是产生一种非常危险的现象：
$$
\boxed{Wrong\ Problem + Powerful\ AI = Efficiently\ Wrong}
$$

# 3. 你提到的 Token 浪费，其实是这个模型的第二个重要价值

你说：

> AI因为错误尝试通过简单工具而解决不了复杂困难问题导致token浪费

这个观察非常准确。

可以把它抽象成：
$$
Problem\ Complexity > Solution\ Representation
$$
例如：

```text
复杂问题
    ↓
AI直接尝试
    ↓
局部修补
    ↓
失败
    ↓
换Prompt
    ↓
再局部修补
    ↓
失败
    ↓
Token × N
```

真正应该发生的是：

```text
复杂问题
    ↓
Human：发现当前表示方式不适合
    ↓
Problem Transformation
    ↓
复杂问题
      ↓
拆解 / 建模 / 降维 / 转换
      ↓
多个可解问题
    ↓
AI分别求解
```

所以：

> **人类介入的价值，不一定是“替 AI 做更多事情”，而是避免 AI 在错误的问题空间里搜索。**

这个非常重要。

# 4. 因此我反而不建议叫它“AI辅助解题 SOP”

这个名字太弱。

你现在实际上提出的是一个：

> **人机协同的问题工程（Problem Engineering）框架。**

我比较推荐一个名字：

# **Problem Engineering Loop（问题工程闭环）**

中文可以叫：

> **问题工程法**

如果想更强调 AI：

> **AI-Native Problem Engineering（AI 原生问题工程）**

核心定义可以写成：

> **问题工程，是通过持续构建、定位、转化和验证问题结构，将复杂现实问题转化为适合人类判断与 AI 求解的可计算、可验证问题集合的过程。**

# 5. 我会把你的 SOP 设计成 5 层

不是传统的：

> 分析 → 设计 → 开发 → 测试

而是：

```text
                    ┌─────────────────────┐
                    │     REAL PROBLEM    │
                    │      现实问题       │
                    └──────────┬──────────┘
                               ↓
                    ┌─────────────────────┐
                    │ ① PROBLEM FRAMING  │
                    │     问题构建        │
                    │                     │
                    │ Why?                │
                    │ 真正的问题是什么？   │
                    └──────────┬──────────┘
                               ↓
                    ┌─────────────────────┐
                    │ ② PROBLEM TREE     │
                    │     问题树          │
                    │                     │
                    │ 哪些问题真正影响结果？│
                    └──────────┬──────────┘
                               ↓
                    ┌─────────────────────┐
                    │ ③ PROBLEM TRANSFORM│
                    │     问题转化        │
                    │                     │
                    │ How Else?           │
                    │ 能不能换一种形式？  │
                    └──────────┬──────────┘
                               ↓
                    ┌─────────────────────┐
                    │ ④ AI SOLVABLE UNIT │
                    │     AI可解单元      │
                    │                     │
                    │ 明确输入/输出/约束   │
                    └──────────┬──────────┘
                               ↓
                    ┌─────────────────────┐
                    │ ⑤ SOLVE & VERIFY   │
                    │     求解与验证      │
                    │                     │
                    │ AI执行，人类判断     │
                    └──────────┬──────────┘
                               │
                               └──────→ 重新构建问题树
```

这个闭环最重要的地方是：

5→1\boxed{5 \rightarrow 1}

**求解结果会反过来改变问题树。**

这才符合真实工程。

# 6. 其中最值得命名的是你的“注意力原则”

我甚至建议把：

> **问题在哪里，注意力就应该在哪里。**

直接升格成这个框架的第一原则：

# **Attention Follows the Problem**

中文：

> **注意力随问题迁移。**

或者更工程化：

> **注意力应集中于当前决定系统结果的关键问题节点。**

这句话非常有价值，因为它解决的是一个非常现实的问题：

### AI时代最大的稀缺资源之一不是算力，而是人的高质量注意力。

于是：

```text
低价值：
────────────────
写代码
查资料
改格式
重复测试
机械重构
生成文档
────────────────
→ 尽可能交给 AI

高价值：
────────────────
问题定义
因果判断
边界判断
关键假设
问题转化
架构取舍
异常识别
停止/转向
────────────────
→ 人类注意力集中
```

这不是“AI取代人”。

而是：

> **重新配置人类注意力。**

# 7. 你的“问题树”还可以进一步成为整个系统的核心数据结构

这个地方我觉得非常有意思。

传统项目管理的核心对象是：

> Task

AI Agent时代，我认为可以进一步变成：

> **Problem**

也就是说：

```text
传统：
Project
  ↓
Epic
  ↓
Story
  ↓
Task
  ↓
Agent
```

你的模型：

```text
现实目标
   ↓
Problem Tree
   │
   ├── Root Problem
   │
   ├── Critical Problem
   │      ↓
   │   Reformulation
   │      ↓
   │   AI-Solvable Problem
   │
   ├── Supporting Problem
   │
   └── Validation Problem
```

于是：

> **Task不再是最基本的管理单位，Problem才是。**

Task只是解决 Problem 的一种执行形式。

这其实和你之前讨论的 **Epic → Sprint → User Story → Feature → Task → Agent** 可以很好地接起来。

```text
                         REALITY
                            │
                            ▼

                    │  ① FRAME      │

                    │     WHY       │
                    └───────┬───────┘
                            │
                            ▼
                    ┌───────────────┐
                    │  ② TREE       │
                    │   问题树       │
                    │ WHERE MATTERS?│
                    └───────┬───────┘
                            │
                     注意力 ↓
                            │
                            ▼
                    ┌───────────────┐
                    │ ③ TRANSFORM   │
                    │   问题转化     │
                    │  HOW ELSE?    │
                    └───────┬───────┘
                            │
                            ▼
                    ┌───────────────┐
                    │ ④ DELEGATE    │
                    │  AI可解问题    │
                    │   WHAT AI?    │
                    └───────┬───────┘
                            │
                            ▼
                    ┌───────────────┐
                    │ ⑤ SOLVE       │
                    │ AI执行/搜索/验证│
                    │     HOW       │
                    └───────┬───────┘
                            │
                            ▼
                    ┌───────────────┐
                    │ ⑥ VERIFY      │
                    │ 结果是否改变问题│
                    │     TREE?     │
                    └───────┬───────┘
                            │
                            └──────────→ ①
```

整个模型可以浓缩成一句话：

> **人负责决定“问题是什么、哪里最重要、还能不能换一种问法”；AI负责在确定的问题空间中进行高吞吐求解；求解结果再反过来修正问题树。**

我认为这比单纯的 **Human-in-the-loop** 更准确。后者只说明“人插入流程”，而你讨论的是：
$$
\boxed{\textbf{Human-in-the-Problem-Loop}}
$$
**人不是站在 AI 执行流程外面审批，而是持续控制“问题空间本身”。**

这可能才是 AI-native 软件工程里非常值得继续展开的一条线：**从 Task-driven Development 转向 Problem-driven Development，再由 Agent 承担 Problem-solving。**

你更想先把它整理成一张适合团队协作的“问题工程闭环”图，还是先把每个环节写成可直接执行的 SOP？
