## 0. 总口径，一句话先把项目讲清楚

老师您好，我们第五组做的是一个基于 RuoYi Vue3 管理后台改造的“常工鲜生”生鲜订购系统。系统不是只做一个单体 CRUD，而是按分布式课程要求拆成 `lgg-admin`、`lgg-business`、`lgg-pay`、`lgg-notice`、`lgg-gateway` 五个微服务，并接入 Nacos 注册发现、Gateway 统一入口、OpenFeign 跨服务调用、RabbitMQ 异步解耦、WebSocket 实时推送、Redis 缓存、MinIO 图片对象存储。现场演示的业务闭环是：后台维护水果分类和商品，小程序浏览加购并提交订单，模拟微信支付后订单状态更新，后台实时收到新订单提醒，管理员再完成接单、派送、完成订单，最后用 Newman 和 Playwright 验证接口和端到端链路。

这套系统的验收重点有三个：

1. 架构闭环：外部请求统一走 Gateway，服务通过 Nacos 注册发现，支付服务通过 Feign 调业务服务，再通过 RabbitMQ 和 WebSocket 推送通知。
2. 业务闭环：小程序下单、支付确认、后台接单、派送、完成、历史订单和工作台统计都能串起来。
3. 工程闭环：PM2 一键维护本地多进程，CLI 测试能复现接口和 WebSocket 推送链路，不依赖口头说明。

### 6.1 用户下单接口

源码位置：

讲解口径：

> 用户下单先进入 `user.OrderController` 的 `/submit`。Controller 不写复杂业务，只做入参接收和调用 Service。真正业务在 `OrderServiceImpl.submitOrder`：先校验地址是否存在，再查当前用户购物车；购物车为空直接抛业务异常；然后按购物车明细计算总金额，生成订单主表，设置订单号、用户、地址、支付状态和订单状态；再批量插入订单明细，最后清空购物车并返回订单号和金额。

要强调的工程点：

- 使用 `@Transactional` 保证订单主表、明细、清空购物车在一个事务里。
- 对 `deliveryStatus`、`packAmount`、`tablewareNumber`、`tablewareStatus` 做默认值兜底，避免数据库 NOT NULL 报错。
- 金额以后端购物车计算为准，避免前端篡改金额。

### 6.2 支付确认和订单状态更新

重点代码：

- `PUT /user/order/payment`
- `PUT /user/order/payment/confirm`
- `OrderServiceImpl.payment`
- `OrderServiceImpl.confirmPayment`
- `OrderServiceImpl.paySuccess`

讲解口径：

> 支付这里分两层。`payment` 方法模拟微信预支付参数，返回小程序调起支付需要的 nonce、timestamp、package、paySign 等字段；因为课程环境没有真实商户证书，所以这里是 mock 参数。支付成功后，`confirmPayment` 或支付服务回调会进入 `paySuccess`。`paySuccess` 会按订单号查订单，把订单从待付款改成待接单，同时把 `payStatus` 改为已支付，并记录支付时间。

要主动解释一个修复点：

> 微信支付回调没有当前登录用户上下文，所以 `paySuccess` 不能只按 `userId + orderNumber` 查。我们做了兼容：先尝试当前用户查询，查不到时，如果订单号是纯数字就兼容按 ID 查询，再查不到就按订单号分页查询。这是为了避免异步回调场景下因为缺少上下文或订单号格式不同导致支付链路中断。

### 7.3 RabbitMQ 投递支付成功事件

重点代码：

```text
MockPayService.pay
```

讲解口径：

> 订单状态更新成功后，支付服务第二步通过 `RabbitTemplate.convertAndSend` 投递支付成功消息。这里不是直接调用通知服务接口，而是通过 RabbitMQ 解耦。这样支付服务只关心“我发出支付成功事件”，通知服务是否在线、什么时候消费，不影响支付状态的主链路。

如果老师问“为什么既有 Feign 又有 RabbitMQ？”

> Feign 用在必须马上成功的同步状态更新：支付成功后订单必须变成已支付。RabbitMQ 用在非核心但要可靠触达的通知链路：后台提醒、语音播报、后续扩展短信或站内信都适合异步消费。同步保证一致性，异步降低耦合。

## 8. 通知微服务讲解：RabbitMQ 消费 + WebSocket 推送

### 8.1 消费支付成功事件

源码位置：

```text
/Users/caolei/Desktop/springboot-lgg/ruoyi-vue-lgg-backend/ruoyi-notice/src/main/java/com/ruoyi/notice/consumer/PaySuccessConsumer.java
```

讲解口径：

> `PaySuccessConsumer` 使用 `@RabbitListener` 监听 `pay.success.queue`，并通过 `@QueueBinding` 声明队列、交换机和 routing key。这样通知服务启动时可以自动声明绑定关系，避免 RabbitMQ 队列不存在导致启动失败。收到订单号后，消费者组装 JSON 消息，再调用 `WebSocketServer.sendToAllClients` 广播给所有在线后台页面。

### 8.2 WebSocket 长连接

源码位置：

```text
/Users/caolei/Desktop/springboot-lgg/ruoyi-vue-lgg-backend/ruoyi-notice/src/main/java/com/ruoyi/notice/websocket/WebSocketServer.java
```

重点代码：

- `@ServerEndpoint("/websocket/{userId}")`
- `ConcurrentHashMap<String, Session> sessionMap`
- `@OnOpen` 保存连接。
- `@OnClose` 移除连接。
- `sendToAllClients` 遍历 session 广播消息。

讲解口径：

> WebSocket 是后台实时提醒的关键。传统 HTTP 是前端主动轮询，延迟和开销都高；WebSocket 建立长连接后，后端可以主动推送。这里用线程安全的 `ConcurrentHashMap` 保存在线 session，收到 RabbitMQ 消息后广播。后台页面就能立即弹出新订单提醒。

老师可能追问“为什么业务服务里也有 WebSocket？”

> 历史迭代中业务服务内也有来单提醒能力；最终微服务化口径是把通知能力独立到 `lgg-notice`，支付服务通过 RabbitMQ 触发通知服务。答辩时主讲 `lgg-notice` 这一条，因为它更符合分布式解耦。

> 分类、商品、订单这些表都有创建时间、更新时间、创建人、修改人。如果每个 Service 都手动 set，会重复且容易漏。我们定义 `@AutoFill` 注解标在 Mapper 方法上，再用 AOP 切面拦截带注解的方法。切面根据 `OperationType.INSERT` 或 `OperationType.UPDATE`，通过反射调用实体的 setter 自动填充公共字段。当前用户 ID 从 `BaseContext` 里取，`BaseContext` 基于 ThreadLocal 保存当前请求用户。

老师可能追问“为什么用反射？”

> 因为不同实体类都有类似字段，但类型不一定继承同一个父类。反射让切面可以以统一方式调用 `setCreateTime`、`setUpdateTime` 等方法，避免为每个实体写重复逻辑。课程项目里这种做法能体现 AOP 横切关注点的价值。

## 14. 常见追问备答

### 14.1 你们这个算不算微服务？

答：

> 算课程设计级微服务。我们至少具备独立进程、独立端口、服务注册发现、统一网关、跨服务 Feign 调用、异步消息解耦和独立通知服务。局限是数据库目前为了本地演示稳定性仍共用一个 MySQL 实例，通过表前缀隔离；报告里也说明了后续可以演进为每个服务独立数据库，再引入 Seata 处理分布式事务。

### 14.2 为什么数据库没有完全拆开？

答：

> 课程答辩强调本地可运行和链路可验收。多库会显著增加初始化、事务和演示风险。我们先完成服务级拆分和通信治理，把数据库作为后续演进点。报告第 6 章也明确写了这是当前局限，后续可以拆成业务库、支付库、通知库，并接入分布式事务。

### 14.3 RabbitMQ 没跑时系统会怎样？

答：

> 支付主链路的订单状态更新依赖 Feign，先于消息投递。RabbitMQ 影响的是通知链路，不应该阻断订单状态更新。生产环境可在发送失败时记录重试表或启用 publisher confirm；课程版本重点展示同步主链路和异步通知链路的分工。

### 14.4 为什么需要 WebSocket？

答：

> 新订单提醒要求低延迟。轮询会浪费请求，并且订单来了可能要等下一次轮询。WebSocket 建立长连接后，后端能主动推送，后台运营人员能即时收到提醒。

### 14.5 为什么支付是 mock？

答：

> 真实微信支付需要商户号、证书、签名、公网回调地址和备案环境，课程本地演示不具备这些条件。我们保留了支付参数生成、支付确认、支付回调、订单状态更新这些核心业务结构，用 mock 代替真实扣款动作。技术上如果接入真实微信，只需要替换支付服务内部的扣款和验签部分，业务服务状态更新逻辑不变。

### 14.6 RuoYi 在这里提供了什么？

答：

> 提供后台基础设施：登录认证、token、RBAC 权限、菜单、角色、用户、字典、日志、前端布局。我们在它上面扩展生鲜业务模块，并把业务模块拆到 `lgg-business` 微服务中。

### 14.7 PM2 和 Maven、Spring Boot 有什么关系？

答：

> Maven 负责构建 jar，Spring Boot 负责应用运行，PM2 负责进程守护。三者不是替代关系。打包后每个服务是一个 jar，PM2 用 `java -jar` 把它们托管起来，并提供状态、日志和自动重启能力。

### 14.8 CLI 测试为什么有 Newman 也有 Playwright？

答：

> Newman 是接口级测试，快，适合验证 REST API。Playwright 是端到端测试，慢一些，但能验证浏览器、WebSocket、支付触发和数据库状态。两者组合能覆盖不同层次。

## 15. 答辩时不要踩的坑

1. 不要说“完全生产级微服务”。应该说“课程设计级微服务，具备服务拆分、注册发现、网关、Feign、MQ、WebSocket 和本地进程治理；数据库物理拆分和链路追踪是后续展望”。
2. 不要把所有状态码说混。小程序订单状态以代码中为准：待付款、待接单、接单/派送/完成等状态要结合页面展示讲，不要临场发明。
3. 不要说 RabbitMQ 是必须让支付成功的组件。订单状态更新靠 Feign，RabbitMQ 是通知解耦。
4. 不要只展示页面。老师要看源码时，优先打开网关配置、订单 Service、支付 Service、通知 Consumer、WebSocket、测试脚本。
5. 不要忽略 PM2。PM2 是演示稳定性的核心证据，也是本项目工程化亮点之一。
