# 国内互联网大厂敏捷开发工业流水线规范

> 整理自字节跳动、阿里巴巴、腾讯、华为、美团等大厂工程实践。覆盖需求到上线全流程规范，可作为团队 SOP 制定参考。

---

## 一、总纲：大厂研发流水线全景图

国内大厂研发流水线高度一致，核心链路为：

```
需求 → 设计 → 开发 → 测试 → 发布 → 运维
```

差异在于各阶段的**深度、工具链、质量门槛和评审节点**。

| 阶段  | 字节跳动             | 阿里巴巴          | 腾讯           | 华为           |
| --- | ---------------- | ------------- | ------------ | ------------ |
| 需求  | OKR驱动 + 精益画布     | 阿里云效 + 敏捷故事地图 | TAPD + 产品需求池 | IPD需求管理      |
| 开发  | GitLab + Go/Goov | 云效 + Java生态   | Git + TGit   | Git + GitLab |
| 测试  | 自动化 + 测试左移       | 工程效能 + AI测试   | CodeReview严苛 | TR评审         |
| 发布  | 滚动发布 + 灰度        | 自动化流水线        | 分支发布模型       | 分层发布         |
| 运维  | 全链路观测            | DevOps        | 蓝翼监控         | ITSM         |

## 二、需求阶段

### 2.1 需求来源与分级

**需求入口（各厂通用）：**

**需求分层（阿里巴巴云效模型）：**
- **Epic**（史诗）—— 战略级目标，如"提升用户留存"
- **Feature**（特性）—— 可独立交付的业务能力
- **Story**（用户故事）—— `作为xxx，我需要xxx，以便xxx`
- **Task / Bug**（任务 / 缺陷）—— 可执行的工作单元

**优先级模型（各厂通用）：**
- P0：核心链路，阻断性问题，**当前迭代必须完成**
- P1：重要功能，下个迭代
- P2：体验优化，后置迭代
- P3：规划外需求，视资源决定

### 2.2 字节跳动需求规范

- **需求冻结**：迭代启动后，需求变更需经过 `AC 评审会` 同意方可加入当期迭代
- **需求澄清（Backlog Grooming）**：Sprint 第二周周二，由 PO 讲解下一迭代需求，研发和测试共同评估故事点
- **INVEST 原则**：每个 Story 必须独立（Independent）、可协商、可估算、短小（2~3天）、可测试
- **验收标准（AC）**：每个 Story 必须有明确的验收条件，无 AC 不进入开发

### 2.3 华为 IPD 需求管理

华为在需求阶段引入 IPD（集成产品开发）的**分层决策机制**：

- **概念阶段（CDCP）**：需求可行性分析，形成 `客户需求规格说明书`，由 IPMT 决策是否立项
- **需求追踪矩阵**：从市场需求 → 产品需求 → 技术规格 → 测试用例，全链路双向追踪
- **$APPEALS$ 模型**：从价格（Price）、性能（Performance）、易用性等八个维度评估需求价值

### 2.4 腾讯需求规范

- **TAPD 需求工作流**：`需求池 → 评审通过 → 排期 → 开发中 → 已提测 → 已上线`
- **需求undo**：每个需求必须关联 Epic / Feature，形成树状结构
- **需求预估**：Story Point 使用斐波那契数列（1, 2, 3, 5, 8, 13），超过 8 分需继续拆分。

## 三、架构设计阶段

### 3.1 方案评审规范

**触发条件（字节/腾讯/阿里通用）：**
- 新项目 / 新服务立项
- 核心架构变更
- 第三方系统接入
- 涉及多团队协作的接口改动

**评审产出物：**
- 系统架构图（分层结构、依赖关系、数据流向）
- 数据库 ER 图 / Schema 设计文档
- 接口 API 文档（优先使用 Swagger / OpenAPI 规范）
- 数据量预估 + 容量规划
- 风险清单及应对方案

**评审参与角色：**
- 主持人（架构师 / TL）
- 后端主研发
- 前端 / 客户端（视情况）
- 测试代表
- 运维 / SRE 代表

**评审通过标准（华为 TR 评审模型）：**
- TR1：需求与概念评审
- TR2：计划阶段技术评审（方案可行性）
- TR3：概要设计评审
- TR4：详细设计评审
- TR4A：模块集成评审
- TR5：可测试性评审
- TR6：正式发布评审

### 3.2 技术选型规范

| 场景 | 字节跳动 | 阿里巴巴 | 腾讯 |
|------|---------|---------|------|
| 小型系统 | Go + 单体 | Java Spring Boot | Go + Tars |
| 中大型系统 | Go 微服务 | Java Spring Cloud / SofaStack | Go + 微服务框架 |
| 前端 | Vue 3 + TS / React |  Vue / React + 中台组件库 | Vue 3 / React |
| 数据库 | TiDB / MySQL | MySQL / PolarDB / OceanBase | MySQL / TDB |
| 缓存 | Redis / ByteDanceCache | Redis / Tair | Redis |
| 消息队列 | Kafka / RocketMQ | RocketMQ / Kafka | CKafka / TDMQ |
| 容器编排 | K8s + 字节自研调度 | K8s + ACK | TKE（腾讯云K8s）|

## 四、开发阶段

### 4.1 Git 分支模型

**字节跳动（主干开发，分支发布）：**
```
main（主干） ← Feature分支开发完成即合并
     ↑
     └── release/x.x.x（发布分支，仅修复hotfix）
```

- Feature 分支开发完成，立即提 MR 合入 main，发起**主干集成**
- 优点：冲突早暴露，集成成本低（从 N² 降至 N 级别）
- 禁止：直接向 release 分支开发新功能

**阿里巴巴（GitFlow 变体 + 云效集成）：**
```
master ←──── feature/xxx（功能分支）
  ↑           └── develop（开发分支）
  └── release/xxx（发布分支）
```

- `develop` 分支：日常开发集成
- `release/` 分支：预发布验证，稳定后合入 master
- Hotfix 从 master 分出，修复后同时合入 master 和 develop

**华为（类似 GitFlow + IPD 阶段门控）：**
- 每个 IPD 阶段对应独立分支验证
- 大型特性通过特性开关（Feature Toggle）控制上线节奏
- TR 评审通过后才允许合入下一阶段分支

### 4.2 代码规范

**各厂统一规范（底线要求）：**

1. **命名规范**
   - 变量 / 方法：驼峰命名（camelCase）
   - 类名：帕斯卡命名（PascalCase）
   - 常量：全大写下划线分隔（MAX_RETRY_COUNT）
   - 禁止拼音命名

2. **函数设计原则（字节/阿里通用）：**
   - 单一职责：每个函数不超过 50 行
   - 无魔法数字：用常量或枚举替代
   - 错误处理：异常必须 try-catch 或统一异常拦截，禁止吞掉异常

3. **注释规范（华为要求最严）：**
   - 所有 public 类 / 方法必须 Javadoc 注释
   - 复杂业务逻辑必须行内注释
   - 禁止注释掉代码（删除而非注释）

4. **禁止规范：**
   - 禁止硬编码配置（必须走配置中心 / 环境变量）
   - 禁止 SQL 拼接（必须参数化查询，防注入）
   - 禁止同步等待外部调用超过超时阈值

**自动化规范（各厂强制）：**
- 代码风格检查：ESLint / Pylint / Checkstyle 集成到 CI
- 安全扫描：SonarQube 门禁，阻塞级问题禁止合入
- 依赖扫描：禁止引入已知漏洞依赖（CVSS ≥ 7.0 阻断）

### 4.3 自测规范

**字节跳动（测试左移，自测驱动）：**
- 单个功能开发完成后，**开发人员必须完成自测**再提交
- 自测必须覆盖：正常数据 + 边界数据 + 异常数据
- 自测覆盖率要求：核心业务单元测试覆盖率 ≥ 70%
- 禁止将未自测的代码提交到共享分支

**华为（TR4 评审包含自测结果）：**
- 每个模块在详细设计评审时必须附带单元测试用例和执行结果
- 华为标准：代码评审（CR）+ 单元测试（UT）+ 集成测试（IT）三件套必须通过才能进入下一 TR

## 五、CodeReview 规范

### 5.1 各厂 CR 机制对比

| 维度 | 字节跳动 | 阿里巴巴 | 腾讯 | 华为 |
|------|---------|---------|------|------|
| 审查范围 | 所有合入 MR | 所有 MR | 所有 MR | 重点模块 TR4+ |
| 审查人数 | ≥ 1人 | ≥ 2人（主R+副R） | ≥ 1人（主R必过） | ≥ 2人（专家+同组） |
| 合并权限 | TL 或高年资授权 | 技术委员会授权 | 项目维护者授权 | IPMT/PDT 授权 |
| 时效要求 | 24h 内响应 | 12h 内响应 | 24h 内响应 | 按评审计划执行 |
| 阻塞条件 | SonarQube 红线 | SonarQube + 安全扫描 | 静态检查全绿 | TR 评审节点 |

### 5.2 CR 检查清单

**代码层面：**
- [ ] 逻辑正确性：边界条件、异常路径
- [ ] 可读性：命名清晰、无嵌套过深（不超过3层 if 嵌套）
- [ ] 重复代码：是否有可抽象的公共逻辑
- [ ] 性能：循环内是否有 DB / RPC 调用（N+1 问题）
- [ ] 安全：鉴权、参数校验、防注入

**设计层面：**
- [ ] 符合架构分层：不在业务层写 SQL、不在工具层写业务
- [ ] 接口向后兼容：新增字段、枚举项处理
- [ ] 数据一致性：事务边界是否正确

**文档层面：**
- [ ] 复杂逻辑有注释说明
- [ ] 新接口有 Swagger 文档
- [ ] 数据库变更有 DDL 脚本

## 六、测试阶段

### 6.1 测试金字塔（各厂通用）

```
           ┌──────────────┐
           │   E2E 测试    │   ← 少量，端到端场景验证
           ├──────────────┤
           │  集成测试     │   ← 中等，模块间交互
           ├──────────────┤
           │  单元测试     │   ← 大量，基础质量保障
           └──────────────┘
```

**关键原则（Google《软件测试之道》）：**
- 85% 的缺陷在开发阶段引入，越早修复成本越低
- 质量不是测出来的，是开发阶段保障的
- 每个开发人员对自己的代码质量负责

### 6.2 测试环境规范

| 环境 | 用途 | 数据要求 |
|------|------|---------|
| DEV | 开发自测 | 构造数据，可随时重置 |
| TEST / SIT | 功能测试 | 脱敏生产数据，数据量足够覆盖场景 |
| UAT | 业务验收 | 真实或高仿真数据 |
| PRE / 集成 | 预发布验证 | 生产级配置，独立数据库 |
| PROD | 正式生产 | 灰度/全量用户 |

**环境隔离规范（字节/阿里）：**
- 环境间禁止混用域名和配置
- 每个环境有独立的数据库和缓存实例
- PRE 环境与生产环境配置一致性 ≥ 99%

### 6.3 灰度发布策略

**各厂灰度模型（由小到大的顺序）：**

1. **金丝雀发布（Canary）**：先发 1~5% 机器，观察错误率
2. **滚动发布（Rolling）**：逐批替换，旧版与新版共存，逐步切流
3. **蓝绿发布（Blue-Green）**：双环境，流量一键切换，可秒级回滚
4. **红黑发布（Red-Black）**：蓝绿变体，流量切换后旧环境自动销毁

**灰度决策指标（各厂核心关注）：**
- 业务指标：订单量、转化率、DAU
- 技术指标：接口错误率、RT（P99/P999）、系统资源
- 告警阈值：错误率超过基线 2 倍立即终止发布

## 七、发布阶段

### 7.1 发布流程规范

**字节跳动发布标准流程：**
```
① 需求冻结确认（PO + 研发 + 测试三方签字）
② PRE 环境验证（必须覆盖全流程）
③ 发布计划通知（至少提前1天通知相关方）
④ 分批次发布（每批间隔 ≥ 15min，观察监控）
⑤ 监控验收（发布后持续观察 30min）
⑥ 发布确认（无异常才算发布成功）
```

**华为发布规范（IPD 阶段门控）：**
- **TR5**（可测试性评审）：测试报告通过后才能申请发布
- **TR6**（发布评审）：最终业务验收 + 合规检查，通过后由 IPMT 授权发布
- 发布必须有**发布单**，记录：变更内容、回滚方案、负责人、验证方案

**腾讯发布规范：**
- 发布窗口：工作日 10:00-18:00（核心业务），夜间发布需提前报备
- 发布必须有**变更经理（Change Manager）** 在场
- 每次发布需提交 `发布检查清单`，逐项打勾

### 7.2 回滚规范

| 触发条件 | 回滚决策 | 回滚时限 |
|---------|---------|---------|
| 核心接口错误率 > 1% | 立即回滚，无需审批 | ≤ 5min |
| 核心链路不可用 | 立即回滚 | ≤ 3min |
| 非核心功能异常 | 评估影响后决策 | ≤ 30min |
| 数据异常 | 立即停止写入，启动数据修复 | — |

**回滚标准操作（字节/阿里/华为通用）：**
1. 停止新版本流量接入
2. 切换回旧版本实例
3. 验证旧版本服务正常
4. 通知相关方（监控告警群 + 业务方）
5. 事后复盘（24h 内输出故障报告）

## 八、运维与稳定性

### 8.1 监控体系

**全链路监控指标体系（各厂统一）：**

- **黄金指标（RED 模型）：**
  - Rate（请求量）：QPS / TPS
  - Errors（错误率）：5xx 占比
  - Duration（延迟）：P50 / P90 / P99 / P999

- **资源指标（USE 模型）：**
  - 利用率（Utilization）
  - 饱和度（Saturation）
  - 错误（Errors）

**告警分级：**
- P0：核心链路不可用，**5分钟内必须响应**
- P1：非核心服务异常，**30分钟内响应**
- P2：性能下降，**2小时内响应**
- P3：预警，无需紧急处理

### 8.2 故障处理规范

**故障处理优先级（华为/字节通用）：**
1. **止血**：先恢复服务，再定位根因
2. **通知**：故障发生 5 分钟内通知相关方
3. **定位**：遵循请求链路逐层排查（网关 → 服务 → DB）
4. **修复**：非紧急修复不得在线 hotfix，必须走发布流程
5. **复盘**：重大故障 24h 内输出 `故障报告（Postmortem）`

**故障报告结构（各厂通用）：**
- 故障时间线（精确到分钟）
- 影响范围（用户量、金额损失）
- 根因分析（5 Why 分析法）
- 改进措施（责任人 + 完成时间）

### 8.3 SRE 稳定性实践

- **错误预算（Error Budget）**：每个季度允许的故障时间窗口，超出后暂停非紧急变更
- **混沌工程**：华为/阿里定期注入故障，验证系统韧性
- **容量规划**：提前评估业务增长，预留 30% 冗余容量
- **SLO / SLA 承诺**：对外承诺服务可用性 ≥ 99.9%，内部 SLO 更严格

## 九、DevOps 与自动化

### 9.1 CI/CD 流水线（各厂标准流水线）

```
代码提交 → 静态检查 → 单元测试 → 构建镜像
    → 安全扫描 → 部署 TEST → 自动化测试
        → 部署 PRE → 人工验证 → 灰度发布 → 全量上线
```

**字节跳动（自研 Build 流水线）：**
- 全链路自动化，代码提交到上线无需人工介入
- 门禁条件：SonarQube 0 阻塞级 + UT 通过率 100% + 安全扫描无高危

**阿里巴巴（云效 Flow）：**
- 流水线和代码托管深度集成
- 支持蓝绿 / 金丝雀 / 滚动多种发布策略
- 内置制品仓库（Artrfactory 兼容）

**华为（自研流水线 + ITSM 集成）：**
- 发布必须关联工单（需求单 / 变更单 / 发布单三单合一）
- 环境变量和密钥统一管理（Vault / 自研密钥中心）

### 9.2 自动化测试要求

| 层级 | 字节 | 阿里 | 腾讯 | 华为 |
|------|-----|------|------|------|
| 单元测试 | ✅ ≥70% | ✅ ≥70% | ✅ ≥60% | ✅ ≥80% |
| 接口自动化 | ✅ 全覆盖 | ✅ 核心链路 | ✅ 全覆盖 | ✅ 全覆盖 |
| UI 自动化 | ✅ 核心场景 | ✅ 回归场景 | ✅ 核心场景 | ⚠️ 重点模块 |
| 性能测试 | ✅ 上线前必做 | ✅ 上线前必做 | ✅ 上线前必做 | ✅ 每版本必做 |

## 十、华为 IPD 敏捷变革实践

华为 IPD 引入敏捷的"三步走"策略，是国内大厂中最具特色的工程实践：

### 第一步：项目级敏捷
- 聚焦单个项目组的开发过程改进
- 引入 Scrum Master + PO 角色
- 实践：持续集成、迭代回顾、自动化测试、站立会议
- 适用阶段：IPD 的 TR2~TR4A 区间

### 第二步：版本级敏捷
- 扩展到 TR1'~TR6 全阶段
- 覆盖架构设计、非研发协同（用服、市场）
- 强调：特性开关控制交付节奏

### 第三步：产品级 / 公司级敏捷
- 多产品线协同
- 引入敏捷发布火车（ART）机制
- 各团队节奏对齐，按固定列车时刻表交付

**华为 IPD + 敏捷的核心价值：**
- 保留了 IPD 的阶段门控（决策评审点）确保投资可控
- 叠加敏捷的快速迭代提升响应速度
- 解决了大型复杂产品的交付效率问题

## 十一、规范落地检查清单

### 需求阶段 ✅
- [ ] 需求有明确的 AC（验收条件）
- [ ] 需求经过评审并有记录
- [ ] 需求已拆分到 Story 粒度（单人 2~3 天）
- [ ] 需求有优先级排序（P0/P1/P2/P3）

### 设计阶段 ✅
- [ ] 架构方案经过评审
- [ ] 接口文档已输出
- [ ] 数据库设计已评审
- [ ] 容量和性能有预估

### 开发阶段 ✅
- [ ] 代码符合命名规范
- [ ] 单元测试覆盖率达标
- [ ] 自测覆盖正常 + 边界 + 异常
- [ ] SonarQube 门禁全绿
- [ ] 安全扫描无高危漏洞

### CodeReview ✅
- [ ] MR 描述清晰（关联需求 + 变更说明）
- [ ] CR 至少 1 人通过
- [ ] CR 提出的问题已修复

### 测试阶段 ✅
- [ ] 功能测试用例全部执行
- [ ] 回归测试覆盖历史功能
- [ ] 性能测试达标（P99 ≤ 目标值）
- [ ] 安全测试无高危

### 发布阶段 ✅
- [ ] PRE 环境验证通过
- [ ] 发布检查清单逐项完成
- [ ] 监控和告警已配置
- [ ] 回滚方案已确认
- [ ] 相关方已通知

### 运维阶段 ✅
- [ ] 监控面板正常
- [ ] SLO 指标在承诺范围内
- [ ] 故障报告已归档
- [ ] 复盘改进措施已落地
