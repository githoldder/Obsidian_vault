# 迪米特法则（LoD / Law of Demeter）

## 📖 定义-解释-示例

### 迪米特法则的经典表述

> **只与你的直接朋友交谈，不跟陌生人说话。**

更技术化的表述：**一个对象应该对其他对象有尽可能少的了解。** 一个方法只能调用以下对象的方法：
1. 对象自身（`this`）
2. 方法参数传入的对象
3. 对象自身创建或实例化的对象
4. 对象的直接组件（成员变量）

**严禁**：调用一个方法的返回值上的方法 → `a.getB().getC().doSomething()`。

迪米特法则的核心哲学：**减少耦合 = 提高可维护性 = 降低变更的连锁反应**。

### 链式调用的破坏力

最直观的违背案例——"火车残骸"代码（Train Wreck）：

```java
// 这种方法违背了迪米特法则的 "火车残骸" 模式
String zipCode = order.getCustomer()
    .getAddress()
    .getCity()
    .getPostalCode();
```

这条链中，当前方法需要知道：
- `Order` 中有 `Customer`
- `Customer` 中有 `Address`
- `Address` 中有 `City`
- `City` 中有 `PostalCode`

**问题**：任何一环的结构变化（比如 `Customer` 不再有 `getAddress()` 而是 `getBillingAddress()` 和 `getShippingAddress()`），这个调用链就断了。更糟糕的是，这个链条上的每一个类都被隐式耦合了——你不需要显式 import 它们，但你的代码依赖了它们内部的导航路径。

**修复方案**：让每个类封装自己的导航逻辑：

```java
// 在 Order 中提供一个封装了导航的方法
class Order {
    public String getCustomerPostalCode() {
        return customer.getPostalCode();
    }
}

// 在 Customer 中封装自己的数据访问
class Customer {
    public String getPostalCode() {
        return address.getCity().getPostalCode();
    }
}

// 调用方——简洁、不越界
String zipCode = order.getCustomerPostalCode();
```

现在调用方只知道 `Order`，不知道 `Customer` → `Address` → `City` 的内部结构。迪米特法则的关键：**结构隐藏**。调用方不需要也不应该知道对象的"朋友的朋友"。

### 迪米特法则 = 最少知识原则

法则要求的不是绝对禁止多级调用，而是**限制当前代码对间接对象的"知识"**。你调用 `a.getB().getName()`，这暗示你知道 `a` 的成员 `B` 有 `getName()` 方法。如果 `B` 换成了 `C`（内部重构），你的代码就要改。

判断公式：**当前方法知道的类 = `this` 的类 + 参数的类 + 返回值 + 成员变量的类 + 自己 new 的类**。除此之外的任何类的任何方法都不应该被调用。你的知识不应该跨越对象边界。

### 迪米特法则 = 不越权

换个角度看，LoD 就是：**不要跨越管理层级。你是部门经理，你不要越过手下经理直接找他的手下的手下**。

```java
// 你不是老板吗？
manager.getTeamLead().getDeveloper().assignTask();
```

这是越权——作为经理，你不应该知道团队领导组织下有哪个开发者的存在。你应该：

```java
manager.assignTaskToTeam("项目A", "前端工作");
```

`manager` 内部自己去找对应的 `teamLead` → 再找对应的开发者 → 分配任务。这些中间的"怎么找"是 `manager` 自己的实现细节，不是外部调用者应该关心的。

### 迪米特法则与其他 SOLID 原则的共鸣

**与 SRP 的关系**：如果 `Order` 通过 `getCustomer().getAddress().getCity()` 获取邮编，`Order` 不仅关心"订单"本身，还隐含地关心了"客户导航路径"。SRP 要求每个类只服务一个参与者，LoD 要求每个方法只了解它的直接朋友。两者合力消灭"知道太多"的类。

**与 ISP 的关系**：胖接口意味着调用方被迫知道很多不需要知道的方法，胖接口调用路径被转递给内部对象的深层结构——LoD 的问题加剧。

**与 DIP 的关系**：当你遵循 DIP（依赖抽象而非具体），你的依赖是从接口定义中来的——而接口通常是"直接朋友"。反之，违反 LoD 的链式调用通常依赖的是具体结构。

### 迪米特法则的边界与权衡

**过度使用的风险**：
如果矫枉过正，会在每个类中塞满"转发方法"（Wrapper / Forwarding Method）：
```java
class Order {
    public String getCustomerName() { return customer.getName(); }
    public String getCustomerEmail() { return customer.getEmail(); }
    public String getCustomerPhone() { return customer.getPhone(); }
    // ... 几十个转发方法
}
```
`Order` 变成了 `Customer` 的镜像接口——这比原始问题更糟。

**实用折中**：
- **稳定的值对象链可以容忍**：`a.getB().getName()` 如果 `B` 是稳定的值对象（如 DTO / 数据类），且未来不会变化，链式调用是合理的
- **不稳定或复杂关系的导航必须封装**：业务对象间的深度导航、可能重构的内部结构——绝对要用方法封装
- **流式 API（Builder Pattern / Stream API）可以例外**：`list.stream().filter(x -> x > 0).map(String::valueOf).collect(toList())` 是在同一个抽象层级上工作（都在操作 `Stream`），不算违背 LoD

### 名言加持

> "The Law of Demeter: talk only to your immediate friends." —— Karl Lieberherr
> "Don't talk to strangers." —— 俗语的精髓在于此

迪米特法则让你在写代码时多问一句："这个方法真的需要知道对象的朋友的朋友吗？" 如果每次的回答都是"不需要"，你的代码会自动朝着高内聚、低耦合的方向演化。
