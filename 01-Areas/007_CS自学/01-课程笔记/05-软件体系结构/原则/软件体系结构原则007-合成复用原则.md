# 合成复用原则（CRP / Composite Reuse Principle）

## 📖 定义-解释-示例 / 比较与对比

### CRP 的经典定义

> **尽量使用对象组合（Composition）/聚合（Aggregation），而不是类继承（Inheritance）来实现复用。**
> —— Gang of Four《设计模式》

也叫**组合/聚合复用原则**。一句话：**"优先组合，其次继承"**。

CRP 是面向对象设计中最容易被忽视但影响最深的原则之一。它直接挑战了"面向对象 = 继承"的直觉认知——恰恰相反，继承可能是你代码中最危险的工具。

### 为什么继承是危险的？

继承通常被美化为"代码复用"的手段。但继承是一把双刃剑：

**继承的问题**：
1. **白盒复用**：子类了解父类的内部实现细节。父类的私有方法改了，子类可能崩。父类的 protected 方法语义变了，所有子类受影响。
2. **编译期绑定**：继承关系在编译时就锁死，运行时无法改变。一个 `Duck` 永远是 `Duck`，你没法让它运行时变成 `PlasticDuck`。
3. **破坏封装**：父类的修改可能"震动"所有子类。这是 LSP 问题的根源——子类的行为依赖父类的内部约定。
4. **只能继承一个**：Java/C# 单继承，想复用两个类的功能？不行。

**继承的正确场景**：只有当子类和父类之间有明确的 **"is-a" 关系**，且行为兼容（满足 LSP），才应该继承。Java 中如果一个类被设计为可继承，那么它应该有个好文档告诉子类："你需要覆盖什么，不要覆盖什么"。

### 组合——CRP 推荐的复用方式

**组合（Composition）** 也叫"黑盒复用"：

```java
// 继承方案——问题多
class Stack extends ArrayList {
    public void push(Object item) { add(item); }
    public Object pop() { return remove(size() - 1); }
    // 问题：外面可以绕过 push/pop 直接 add() / remove()！
}

// 组合方案——合理
class Stack {
    private ArrayList list = new ArrayList();  // 组合
    
    public void push(Object item) {
        list.add(item);
    }
    
    public Object pop() {
        return list.remove(list.size() - 1);
    }
    // list 是私有的，外部无法破坏 Stack 的 LIFO 语义
}
```

组合的 `Stack`：
- `list` 是私有的，外部不可见 → 无法破坏 LIFO 约束
- 以后换 `LinkedList`？改一行：`private LinkedList list = new LinkedList();` → 外部无感
- 外部只能通过 Stack 暴露的 push/pop 操作数据 → 契约得以强制

**组合 vs 聚合**：
- **组合**：强关系。`Stack` 拥有 `list`，`Stack` 销毁时 `list` 也销毁。`"包含"` 关系
- **聚合**：弱关系。`Department` 聚合了 `Employee` 列表，但 `Department` 不存在时 `Employee` 仍然存在。`"拥有"`关系

### 继承 vs 组合——决策表

| 场景 | 用继承 | 用组合 |
|------|--------|--------|
| "is-a" 关系明确且稳定 | ✅ | - |
| 需要复用代码但不想暴露父类接口 | - | ✅ |
| 运行时需要改变行为（策略模式） | - | ✅ |
| 需要复用多个类的功能 | - | ✅ |
| 父类会频繁变化 | - | ✅ |
| 想让子类 100% 继承父类行为且不修改 | ✅ | - |
| 存在 LSP 违反风险 | - | ✅ |

经验法则：**当你不能 100% 确定一个正确的 is-a 关系时，默认用组合。** 组合的成本低，重构简单；错误的继承重构成本高，因为大量代码已经依赖了继承层级。

### 实际案例：策略模式是组合的极致应用

```java
// 鸭子游戏的糟糕继承设计
class Duck {
    public void quack() { ... }
    public void fly() { ... }
    public void swim() { ... }
}
class RubberDuck extends Duck {
    @Override public void quack() { /* 吱吱叫 */ }
    @Override public void fly() { /* 不会飞！空实现 */ }  // LSP 违背！
}
class DecoyDuck extends Duck {
    @Override public void quack() { /* 不叫 */ }           // 空实现
    @Override public void fly() { /* 不会飞 */ }            // 空实现
}
```

**组合重构——策略模式**：

```java
interface QuackBehavior { void quack(); }
interface FlyBehavior { void fly(); }

class Quack implements QuackBehavior { public void quack() { /* 呱呱 */ } }
class Squeak implements QuackBehavior { public void quack() { /* 吱吱 */ } }
class MuteQuack implements QuackBehavior { public void quack() { /* 不叫 */ } }

class FlyWithWings implements FlyBehavior { public void fly() { /* 飞 */ } }
class FlyNoWay implements FlyBehavior { public void fly() { /* 不飞 */ } }

class Duck {
    private QuackBehavior quackBehavior;  // 组合
    private FlyBehavior flyBehavior;      // 组合
    
    public void performQuack() { quackBehavior.quack(); }
    public void performFly() { flyBehavior.fly(); }
    
    public void setFlyBehavior(FlyBehavior fb) { this.flyBehavior = fb; }  // 运行时可换！
}
```

现在：
- `MallardDuck` = `Duck` + `Quack` + `FlyWithWings`
- `RubberDuck` = `Duck` + `Squeak` + `FlyNoWay`
- `DecoyDuck` = `Duck` + `MuteQuack` + `FlyNoWay`

不再有空实现。不再有 LSP 违背。行为可在运行时动态改变（`setFlyBehavior`）。这就是组合超越继承的全部理由。

### CRP 与其他 SOLID 原则的协同

**CRP + DIP**：组合的对象类型应该是接口/抽象类型（DIP），而不是具体类。`Duck` 组合的是 `FlyBehavior` 接口，而不是 `FlyWithWings` 实现。

**CRP + SRP**：用组合拆分职责，每个组件只做一件事。`QuackBehavior` 只关心叫，`FlyBehavior` 只关心飞。

**CRP + LSP**：如果继承关系下出现 LSP 违背，组合通常是正确的逃生路线。

**CRP + OCP**：组合让你可以添加新行为（新策略）而不修改已有类。添加 `RocketFly` 类即可，不动任何已有代码。

### 名言加持

> "Favor object composition over class inheritance." —— GoF《设计模式》
> "继承是面向对象最过度使用的特性。" —— 无数重构过屎山代码的程序员的心声

对于初学者，"继承就是面向对象"的刻板印象必须被纠正。继承是一种工具，不是一种信仰。合成复用原则提醒我们：当你需要复用代码时，先想组合，只有组合不能满足时才考虑继承。
