# 哈希表（Hash Table）

## 📖 理论与实践

### 什么是哈希表？

**哈希表**是一种基于**键值对（Key-Value Pair）**的数据结构，核心思想：通过**哈希函数**将键（key）映射到数组中的索引位置，从而在 **O(1) 平均时间复杂度**下实现插入、删除和查找操作。

数据结构世界有一条铁律：**如果可以用数组索引直接访问，就是 O(1)；如果需要遍历，最坏是 O(n)。** 哈希表通过哈希函数把键"翻译"成数组索引，实现了"通过键直接跳转到数据位置"的效果。

### 哈希表的核心三要素

**1. 哈希函数（Hash Function）**
输入任意键 → 输出数组范围内的整数索引。好的哈希函数：
- **确定性**：同一个键始终映射到同一个索引
- **均匀分布**：不同键的哈希值应均匀分散到所有索引，减少冲突
- **快速计算**：哈希本身不应对性能造成显著影响

简单示例（整型键）：`hash(key) = key % tableSize`

对字符串键：`hash(s) = (s[0] × 31^(n-1) + s[1] × 31^(n-2) + ... + s[n-1]) % tableSize`

Java 中 `String.hashCode()` 的实现（霍纳法则）：
```java
public int hashCode() {
    int h = 0;
    for (int i = 0; i < value.length; i++) {
        h = 31 * h + value[i];
    }
    return h;
}
```
选择 31 是因为它是奇素数——乘法可以用移位优化（`31 * h = (h << 5) - h`），且素数有助于减少哈希冲突。

**2. 数组（Bucket Array）**
每个索引位置称为一个**桶（Bucket）**。桶可以直接存一个元素，也可以存多个元素（冲突处理）。

**3. 冲突处理（Collision Resolution）**
不同的键可能哈希到同一个索引——这就是**哈希冲突**。冲突是必然的（鸽巢原理：无限多的键映射到有限多的索引），关键是冲突后的处理策略。

### 两种主流冲突处理策略

**链地址法（Separate Chaining）**
每个桶是一个链表（或红黑树）。发生冲突时，新条目追加到链表中。Java `HashMap` 默认使用此方法。

```
桶 0: (keyA, valA) → (keyB, valB) → null    ← 冲突！keyA 和 keyB 哈希到同一个桶
桶 1: (keyC, valC) → null
桶 2: null
桶 3: (keyD, valD) → null
```

**查找过程**：
1. 计算 `hash(key)` → 定位桶索引
2. 遍历该桶的链表，用 `equals()` 逐个比较键，找到匹配的条目
3. 如果链表长度超过阈值（Java 8+ 默认为 8），链表转换为**红黑树**，优化为 O(log n) 搜索

**开放寻址法（Open Addressing）**
所有条目存在数组本身。冲突后按固定规则寻找下一个空位：
- **线性探测**：`index = (hash + i) % tableSize`，i=0,1,2...（简单但会"聚集"）
- **二次探测**：`index = (hash + i²) % tableSize`（减少聚集）
- **双重哈希**：`index = (hash1 + i × hash2) % tableSize`（最佳分布）

开放寻址对缓存友好（数据连续），但在高装载因子下性能急剧下降。Python 的 `dict` 和 Lua 的 `table` 使用开放寻址。

### 哈希表的扩容（Rehashing）

当装载因子（Load Factor = 元素数量 / 桶总数）超过阈值时，哈希表性能恶化。Java `HashMap` 默认阈值 = 0.75。

**扩容过程**：
1. 创建一个更大的新数组（Java `HashMap` 默认扩容为原来的 2 倍）
2. 将旧表中每个条目重新哈希，放入新表的对应位置
3. 扩容是 O(n) 操作——这也是哈希表在特定时刻会"卡"一下的原因

**为什么默认是 0.75？**
时间与空间的折中。0.75 意味着容器在还有 25% 空桶时就开始扩容——留给冲突一定的弹性，不会频繁触发扩容。如果设为 0.5（更保守），浪费空间；设为 0.9（更激进），冲突更多、搜索慢。

### Java HashMap 的关键实现细节

**`HashMap` vs `Hashtable` vs `ConcurrentHashMap`**：
| 类型 | 线程安全 | null 键/值 | 性能 | 推荐 |
|------|----------|------------|------|------|
| `HashMap` | ❌ | 允许 null 键和值 | 最快 | 单线程 |
| `Hashtable` | ✅（synchronized） | 不允许 null | 慢（全局锁） | 已淘汰 |
| `ConcurrentHashMap` | ✅（分段锁/CAS） | 不允许 null | 较好 | 多线程首选 |

**`HashMap` 内部结构**（Java 8+）：
- 主体是 `Node<K,V>[] table` 数组
- 冲突少 → 链表。链表长度 ≥ 8 且数组长度 ≥ 64 → **红黑树化**（TreeNode）
- 红黑树节点数 ≤ 6 → 退化回链表
- 树化的阈值选择：链表 O(n) vs 红黑树 O(log n) 的交叉点；泊松分布下链长到 8 的概率约为 0.00000006

**`LinkedHashMap`**：`HashMap` 的子类，额外维护双向链表记录插入顺序或访问顺序。适合 LRU 缓存场景。

**`TreeMap`**：红黑树实现，不是哈希表。按键的自然顺序排序，操作 O(log n)。适合需要有序遍历的场景。

### 哈希表的时间复杂度

| 操作 | 平均 | 最坏 |
|------|------|------|
| 插入 | O(1) | O(n)（所有键哈希到同一桶，退化为链表） |
| 查找 | O(1) | O(log n)（Java 8+ 树化后）/ O(n) |
| 删除 | O(1) | O(log n) / O(n) |

**最坏情况何时发生？**
1. 选了一个很差的哈希函数，所有键都返回相同的哈希值
2. 攻击者精心构造键使它们哈希冲突（HashDoS 攻击）——这就是 Java 8 引入红黑树的原因：从 O(n) 退化为 O(log n)，防御拒绝服务攻击

### 哈希表的常见应用

- **数据库索引**：哈希索引（等值查找极快，但不支持范围查询）
- **缓存系统**：`HashMap`/`ConcurrentHashMap` → 本地缓存、Redis（键值存储的精髓就是哈希表）
- **去重**：`HashSet`（内部使用 `HashMap`，值存一个占位符） → 邮件去重、URL 去重
- **计数**：邮件中单词频率统计 = `HashMap<String, Integer>` → 单词为键，词频为值
- **路由表**：IP 地址 → 下一跳的映射（TCAM 硬件实现本质也是哈希表变体）
- **编译器符号表**：变量名 → 类型/作用域/内存偏移

### 哈希表 vs 数组 vs 平衡树

| 维度 | 哈希表 | 有序数组 | 平衡二叉树 |
|------|--------|----------|------------|
| 精确查找 | O(1) avg | O(log n) | O(log n) |
| 范围查找 | 不支持 | O(log n + k) | O(log n + k) |
| 插入/删除 | O(1) avg | O(n) | O(log n) |
| 有序性 | ❌ | ✅ | ✅ |
| 内存占用 | 中（桶数组 + 节点开销） | 低（紧凑） | 高（指针开销） |
| 什么时候用 | 只需精确查找 | 需要有序，数据不变 | 需要有序，数据变化频繁 |

哈希表牺牲了有序性和理论最坏时间，换取了实际中最快的 O(1) 操作。这种取舍在日常业务代码中几乎永远正确——你通常关心的是"通过用户 ID 查用户信息"，不是"列出 ID 在 100-200 之间的所有用户"。
