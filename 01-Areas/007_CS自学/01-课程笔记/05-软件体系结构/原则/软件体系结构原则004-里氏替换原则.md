# 里氏替换原则（LSP / Liskov Substitution Principle）

## 📖 定义-解释-示例

### LSP 的经典定义

> **如果 S 是 T 的子类型，那么在任何使用 T 对象的地方，都可以用 S 对象替代，而程序的行为不会发生改变。**
> —— Barbara Liskov（1987 年图灵奖获得者）

通俗翻译：**子类应该可以无缝替换父类，而使用父类的代码不需要做任何修改或特殊判断**。如果替换后程序崩了、结果变了、或者需要加 `if (obj instanceof SubClass)` 来判断，那就是违背了 LSP。

### LSP 的本质——行为兼容

LSP 不是关于"语法兼容"（Java 编译器检查继承关系），而是关于**行为兼容**。编译器不管你子类做了什么（只要方法签名对得上），但 LSP 要求的是行为上的"不出意外"。

经典违反案例——矩形与正方形：

```java
class Rectangle {
    protected int width;
    protected int height;
    
    public void setWidth(int w) { this.width = w; }
    public void setHeight(int h) { this.height = h; }
    public int getArea() { return width * height; }
}

class Square extends Rectangle {
    @Override
    public void setWidth(int w) {
        super.setWidth(w);
        super.setHeight(w);  // 正方形：宽=高
    }
    
    @Override
    public void setHeight(int h) {
        super.setHeight(h);
        super.setWidth(h);   // 正方形：宽=高
    }
}
```

看起来合理？来看这段代码：

```java
void resize(Rectangle r) {
    r.setWidth(5);
    r.setHeight(10);
    assert r.getArea() == 50;  // 期望：5 × 10 = 50
}
```

传入 `Rectangle` → 通过。传入 `Square` → `setWidth(5)` 把高也设为 5，然后 `setHeight(10)` 把宽也设为 10，结果面积是 **100** 而不是 50。断言失败。**`Square` 不能替代 `Rectangle`**——违背了 LSP。

**教训**：在数学上"正方形是矩形"是正确的主语-谓语关系；但在面向对象编程中，只有在**行为不退化**的前提下，继承才有意义。正方形"设定宽"的行为（强制同步高）与矩形"设定宽"的行为（独立操作）不一致 → 不应该继承。

### LSP 的四个约束条件

要让子类能安全替换父类，必须满足：

**1. 前置条件不能加强（Contravariance of Preconditions）**
子类方法要求的条件不能比父类更苛刻。父类 `deposit(amount)` 要求 amount > 0，子类不能要求 amount > 100。调用方按照父类的契约传入 amount=50，结果子类报错——替换失败。

**2. 后置条件不能减弱（Covariance of Postconditions）**
子类方法保证的结果不能比父类更差。父类 `withdraw(amount)` 确保"取款后余额必然减少 amount"，子类不能在某条件下"跳过取款操作"。

**3. 不变量要保持（Invariant Preservation）**
父类所保证的不变条件（比如"余额永远 ≥ 0"）在子类中必须继续成立。

**4. 历史约束（History Constraint）**
子类不能引入父类没有的、改变状态的方式。比如父类只有 `add()` 和 `remove()`，子类偷偷加了一个 `clear()` 被外部直接调用——父类的客户端不知道有 `clear()` 这个操作，这算是一种行为破坏。

### 实际场景中的 LSP 违背

**场景 1：抛出父类未声明的异常**
```java
class FileStore {
    public String read(String key) { return "data"; }
}

class DatabaseStore extends FileStore {
    @Override
    public String read(String key) {
        if (connection == null)
            throw new DatabaseException("Not connected");  // 父类没有这个异常！
        return super.read(key);
    }
}
```
使用 `FileStore` 的代码没有准备处理 `DatabaseException`。替换失败。

**场景 2：返回结果语义不同**
父类 `findUser(id)` 找不到时返回 null。子类 `findUser(id)` 找不到时返回一个空的 `User` 对象（`new User()`）。外部代码检查 `if (user == null)` 来判断用户是否存在 → 换了子类后逻辑完全不同。

**场景 3：子类"消失的方法"**
```java
class Bird {
    public void fly() { System.out.println("Flying!"); }
}

class Penguin extends Bird {
    @Override
    public void fly() {
        throw new UnsupportedOperationException("Penguins can't fly!");
    }
}
```
这比前两个更灾难性。编译通过，运行时爆炸。企鹅不应该继承会飞的鸟——这是对继承的滥用。

### LSP 告诉你：何时不该用继承

LSP 最大的价值不是告诉你"怎样写好的继承"，而是告诉你**"什么时候不该用继承"**。

如果子类需要：
- 覆盖方法并改变行为语义（不是增强，是改变）
- 在覆盖的方法中抛出新异常
- 在覆盖的方法中什么都不做（空实现 = 父类的契约未履行）
- 在覆盖的方法中添加父类没有的额外约束

→ 说明这不是一个继承关系。使用**组合**或提取**共同接口**来替代。

### LSP 的修复策略

对于矩形-正方形的例子，正确的设计是两者都实现 `Shape` 接口（或继承自抽象基类），用组合代替继承：
```java
interface Shape { int getArea(); }

class Rectangle implements Shape { ... }  // 独立实现
class Square implements Shape { ... }     // 独立实现
```

关键洞察：如果两个类的行为预期不同，**就不应该强制它们共用一套接口的约定**，即使它们在"常识"中有从属关系。LSP 是用代码的行为约束来反转了我们对"是什么"的常识判断。
