# 文心阁设计和开发文档

## 第一章 需求分析

### 1.1 项目背景与问题界定

“文心阁”是一套面向高校文科用户，尤其是汉语言文学、古典文学、文献学、古代汉语及相关人文学科学生与教师的数字化学习与研究平台。其建设初衷并不在于提供一个泛娱乐化的诗词浏览网站，也不意在复制一个通用型的大模型聊天壳层，而是试图在古典文学学习链条中，建立一条具有学术针对性的工作路径：从文献检索进入文本细读，从文本细读过渡到个人札记沉淀，再由札记与原文共同支撑后续的问答、整理与知识重组。传统搜索引擎虽然具备信息覆盖面的优势，但其检索结果分散、噪声较多，且无法对诗词原文、作者背景、注释译文与个体笔记之间的关系进行统一组织；普通笔记工具虽然具备记录能力，却难以承载古典文学学习中高频出现的“文本—作者—主题—意象—个人理解”多重映射；通用大模型尽管可以提供一定程度的解释与生成，却常常缺乏证据约束和学术语境感，难以直接服务于课程研读、专题整理和论文准备。因此，文心阁试图解决的，并非单一页面层面的交互问题，而是一种长期存在于文科研究场景中的方法论断裂问题。

从现实需求层面来看，用户在进行古典文学学习时往往需要完成四项相互纠缠的任务。其一，迅速找到可信且结构化的文本对象，包括作品标题、作者、朝代、原文、注释、译文与赏析。其二，将阅读过程中形成的理解、摘录与疑问沉淀为可持续增长的个人知识资产，而不是一次性消费的信息片段。其三，在多篇作品与多条笔记之间建立可导航的连接，使学习不再停留在孤立条目层面。其四，在需要生成阶段性理解、梳理逻辑链条或扩写学术表达时，引入具备上下文感知能力的智能助手辅助用户完成整理。文心阁的提出，正是围绕这四项需求展开。若以图表形式呈现，建议在本章补充“古典文学学习场景问题链路图”与“用户任务流程图”，以进一步增强需求定义的直观性和完整性。

### 1.2 目标用户与使用场景

本项目的核心目标用户是高校中文系学生、古典文学研究生、课程教师及具有系统性古典阅读需求的人文学习者。与 K12 场景下强调知识点讲解和练习反馈的工具不同，文心阁面向的对象通常具备一定文本阅读基础，其痛点不在于“看不懂一首诗”，而在于无法高效地把零散阅读经验组织成可复用、可检索、可追溯的知识网络。用户在备课、准备课程论文、进行考试复习、整理阅读材料或围绕某一文学专题开展长时段研究时，往往需要频繁在“查资料”“摘文本”“做笔记”“看关联”“问问题”之间来回切换。系统若不能在交互层面提供连贯闭环，在数据层面提供统一表示，在智能层面提供受控辅助，学习效率与知识保真度都会受到显著影响。

基于以上判断，文心阁将主要使用场景划分为三类。第一类场景是文库检索与研读场景，即用户围绕作品标题、作者、朝代、主题、意象或自然语言问题发起检索，并在结果页与详情页中完成文本细读与关联探索。第二类场景是札记沉淀与网络化组织场景，即用户将阅读过程中筛选出的作品内容转写为 Markdown 札记，通过文件树、双向链接和图谱视图建立个人知识结构。第三类场景是解惑与整理场景，即用户在已有会话上下文的支撑下，通过 AI 对话完成内容解释、问题追问与阶段性总结。值得强调的是，这三类场景并非彼此割裂，而是构成一条连续的学习链：文库负责材料输入，札记负责知识沉淀，解惑负责调用与重组。

### 1.3 功能需求分析

从功能层面看，文心阁的需求可分为文库模块需求、札记模块需求、解惑模块需求以及系统级支撑需求。文库模块必须支持真实数据驱动的作品展示，而不能停留在静态样板页层面。因此，系统需要具备作品列表查询、作品详情读取、关键词与语义联合检索、关联推荐、收藏与收藏夹管理、搜索日志记录等能力。由于古典诗词在结构上具有显著差异，系统还需要在展示层面对诗与词实施差异化排版策略，使诗句的整齐句法与词牌长短句的节奏感得到保留，避免原始数据库字符串直出造成阅读体验破碎。

札记模块的需求更具结构复杂性。一方面，系统需要提供新建文件夹、新建笔记、重命名、删除、搜索、自动保存、导出 Markdown、导出 PDF 等基础能力；另一方面，考虑到项目后期演进方向，札记正文不能仅依附于数据库字段存在，而应具备本地文件化、可迁移、可扫描、可重建的 Local-First 特征。因此，系统必须围绕真实 Markdown 文件建立文件树、元数据同步与图谱同步机制。与此同时，为支撑知识网络构建，札记模块还必须支持 `[[笔记名]]` 形式的双向链接候选联想、胶囊化渲染、点击跳转与反向链接查看，并进一步在图数据库中将链接关系表达为 Note 节点与 LINKS_TO 边的拓扑结构。

解惑模块的功能需求则聚焦于会话持续性与智能输出质量。系统需要支持流式输出、多轮对话、历史会话列表、新建会话、删除会话和上下文记忆，并在界面上维持足够克制且具有书卷气的交互风格。值得注意的是，解惑模块并非完全等同于札记侧边栏中的 Copilot。两者在产品定位上相互独立：前者是面向用户的问答与分析空间，后者则是嵌入札记工作流中的局部润色与写作辅助面板。除此之外，系统级还需要满足用户鉴权、邮箱验证码注册、JWT 登录状态管理、个人中心资料维护以及环境配置统一加载等要求。

### 1.4 非功能需求分析

非功能需求方面，本项目至少包含可用性、可扩展性、一致性、安全性和可维护性五个层面的约束。首先，在可用性方面，系统必须确保页面交互稳定、响应自然，特别是在高分屏与普通分辨率设备之间应保持良好的版式自适应；其次，在可扩展性方面，系统应为后续 Grounded QA、OCR 接入、更复杂的 GraphRAG 与本地工作区生态演进预留结构空间，而不能将当前实现写死为一次性原型；再次，在一致性方面，前端状态、PostgreSQL 元数据、本地 Vault 文件和 Neo4j 图谱之间需要维持尽可能可靠的同步关系，否则笔记内容、链接关系与可视化结果将出现偏移；在安全性方面，项目需要通过 JWT、邮箱验证码、密码哈希存储和受限文件路径解析等方式规避基础安全风险，特别是本地文件系统模式下必须严防路径穿越与越权写入；最后，在可维护性方面，代码应保持模块边界清晰，配置全部来自 `.env`，并尽量避免将业务逻辑写入无法复用的视图层中。若用于正式比赛答辩或课程提交，建议在本章后附“功能需求—实现映射表”与“非功能需求—技术措施对照表”。

## 第二章 概要设计

### 2.1 设计目标与总体原则

文心阁的概要设计遵循“分层清晰、数据职责明确、界面闭环驱动、后续升级可持续”的总体原则。项目并未采用单一数据库承载全部数据，也未将智能能力粗暴地拼接为附属功能，而是围绕产品主路径，将不同数据形态放置到最适合其职责的存储与服务层中。这一设计的核心思想在于：结构化业务数据应由关系型数据库维护，图结构关系应交由图数据库表达，瞬时或高频访问状态可由 Redis 承担辅助作用，而个人札记的正文作为用户真正关心的知识资产，则应尽可能以可见、可导出、可迁移的本地 Markdown 文件形式存在。

在前端层面，项目以 Next.js 为主框架，围绕“文库—札记—解惑”三个模块组织顶层导航与页面状态管理，通过组件化方式承接检索、会话、文件树、知识图谱、Markdown 编辑器和登录页等复杂交互。前端设计并不追求过度装饰，而是在整体学术气质之下，通过适度的过渡动效、留白、玻璃质感和低饱和色彩组织界面层次，力图在古典阅读场景和现代 Web 工作台之间取得平衡。后端则采用 FastAPI 提供 REST 与流式接口，通过服务层拆解为检索服务、札记服务、图谱服务、聊天服务、鉴权服务、邮件服务与 Vault 文件服务，从而将业务复杂度从路由层剥离出去。

### 2.2 系统总体架构

从总体结构上看，文心阁可以被理解为一个“前后端分离、多存储协同、AI 能力外挂式接入”的复合系统。前端作为统一入口，承载了用户可见的三大业务模块以及登录注册流程；FastAPI 后端作为业务中枢，负责配置加载、数据库初始化、接口聚合、文件系统读写、图谱同步和大模型调用；底层则通过 PostgreSQL、pgvector、Neo4j、Redis 与本地 Vault 共同支撑系统运行。若以图示表达，建议在本节补充一张“系统总体架构图”，其中应明确标出前端展示层、API 服务层、存储层和模型服务层之间的依赖方向与数据流向。

更进一步地说，本系统并非单一数据流，而是至少存在三条并行而交叉的处理链路。第一条是文库链路，即作品主数据从规范化 JSON 导入 PostgreSQL，经由作品查询、搜索与关联接口返回前端。第二条是札记链路，即用户在前端触发创建、编辑和删除操作后，正文优先落盘为 Markdown 文件，再由后端同步元数据到 PostgreSQL，并将双向链接关系同步到 Neo4j。第三条是问答链路，即用户发送问题后，由后端组装上下文消息并向阿里百炼兼容接口发起调用，再以 SSE 形式流式返回前端，同时将历史消息落库以形成持久会话。正是这种多链路协同，使项目能够同时满足阅读、写作与问答三种不同节奏的使用需求。

### 2.3 数据职责划分与存储协同

在存储职责设计上，文心阁采用了明确的“分而治之”策略。PostgreSQL 主要负责存储结构化业务数据，包括作品、作品分块、注释、译文、赏析、收藏夹、搜索记录、聊天会话、聊天消息、用户信息以及札记元数据等。这一设计使系统能够充分利用关系型数据库在事务一致性、复杂查询和模式约束方面的优势。pgvector 扩展则在 PostgreSQL 体系内部提供向量字段及相似度检索能力，使得语义检索无需额外引入独立向量数据库，从而降低了部署复杂度并强化了现有数据模型的一体化。

Neo4j 的职责则严格限定在关系拓扑表达层面。在本项目中，Neo4j 一方面承接由 `all_data.json` 提取出的作品关系增强信息，另一方面承接札记模块中由 `[[双向链接]]` 产生的 Note 节点关系。也就是说，Neo4j 不再承担大段正文存储，而是聚焦于“谁与谁相连、通过何种语义相连”的结构化图关系。这样的划分既避免了文本冗余，也有利于后续在关联推荐、知识图谱可视化和图驱动问答方向继续演进。至于 Redis，目前主要作为缓存与状态扩展预留层；虽然在当前版本中并未承担全部核心路径，但其存在为后续验证码、会话缓存与热点数据响应优化提供了基础。

### 2.4 部署结构与运行方式

系统当前采用 Docker Compose 统一管理核心基础设施，包含 PostgreSQL、Neo4j、Redis 与后端容器。前端在开发阶段使用 Next.js 本地开发服务器运行，通过代理或直接访问 API 路径与后端联调。后端启动时会自动初始化 PostgreSQL 表结构，并扫描本地 Vault 目录，确保笔记系统在服务启动后即可进入可用状态。由于 PostgreSQL 宿主机默认端口易与本地环境发生冲突，项目实际将其映射至 `5433` 端口，这一点在部署说明中必须明确注明，以避免数据库连接误判。建议在本章结尾补充“部署拓扑示意图”与“容器依赖关系图”，以增强概要设计的表达完整度。

## 第三章 详细设计

### 3.1 文库模块详细设计

文库模块的详细设计建立在统一 canonical schema 的前提之上。项目首先通过数据标准化脚本读取 `tang.json` 与 `song.json`，将其中作品标题、作者、朝代、正文、注释、译文与赏析等字段统一映射到标准模型，并为每条作品生成稳定的 `item_id`。其中，唐诗使用 `poem:{dataset_id}`，宋词使用 `ci:{dataset_id}` 作为正式对外标识，这一规则避免了以标题作为主键所带来的同名歧义，也为后续收藏、札记引用和问答追踪提供了稳定键值。与此同时，`all_data.json` 并不直接作为主接口数据源，而是用于提取图谱增强关系，从而保证前端始终面向统一、可控的业务结构消费数据。

在检索实现上，文库模块当前已从单纯关键词 LIKE 检索演进为更复杂的混合检索形态。用户输入查询后，系统会结合关键词命中、语义向量召回和图谱关联信号对候选结果进行综合排序，并返回命中理由、匹配片段与相关度评分。前端在展示层中进一步将这些检索信号解释为“命中原因”“相关度”等易于理解的界面元素，从而提升语义检索的可解释性，避免用户产生“结果虽出来但无法理解为何命中”的不信任感。关联推荐部分则不再以“同朝代”作为粗暴兜底，而是优先考虑作者、主题、意象、词牌或体裁等更具文学相关性的共享节点，并在质量不足时宁可返回空态，也不强行拼接低质量推荐。

在界面组织上，文库采用主卡、搜索结果区与关联探索区三层结构。主卡承担当前焦点作品的展示任务，搜索结果区承担多结果并列比较功能，关联探索区则鼓励用户从单篇阅读扩展到专题阅读。点击“查看全文”后，用户将进入沉浸式详情弹窗。在该弹窗中，左侧集中展示作品标题、作者、出处与原文排版，右侧集中展示译文、鉴赏与背景说明，从而形成“原文阅读”和“辅助理解”并置的双栏结构。近期迭代还针对 1K 屏与高分屏做了自适应修正，使详情弹窗能够避开顶栏遮挡并在较小屏幕上保持完整可视。

### 3.2 札记模块详细设计

札记模块是本项目最具技术辨识度的部分。与传统 Web 笔记系统将正文长期存放于数据库中的方案不同，文心阁将 Markdown 文件作为札记正文的主真源。具体而言，前端的编辑操作最终会写入本地 Vault 中的 `.md` 文件，而 PostgreSQL 仅保留标题、路径、时间戳、工作引用、链接索引等元数据。后端在服务启动和特定操作之后会扫描 Vault，刷新文件树和元数据索引，从而确保本地文件改动、Web 改动和数据库状态尽可能一致。这一机制既保留了 Web 端管理的便利，又给予用户对本地知识资产的真实控制权。

从交互层看，札记左侧文件树支持文件夹展开、收起、搜索、新建、重命名与删除。近期实现中，新建文件夹和新建笔记已取消原生 `prompt` 弹窗，改为直接创建默认名为“未命名”的节点，并立刻进入行内重命名状态；若用户不输入新名称，则默认名保留。同时，系统会在同一目录内部自动检查重名冲突，必要时生成“未命名 2”“未命名 3”等唯一名称，以避免路径层面的覆盖与歧义。中部编辑区则基于 Tiptap 构建，在保留 Markdown 语义的同时提供较为沉浸的输入体验，包括自动保存、导出 Markdown、导出 PDF、字号与留白优化以及划词悬浮工具条等能力。由此，用户既可以用接近所见即所得的方式编辑，又不会失去 Markdown 作为纯文本格式的可迁移性。

双向链接系统的实现涉及前后端协同。当前端检测到用户输入 `[[` 时，会触发候选面板，候选内容来自真实笔记列表与部分文库实体，并按更新时间与匹配度排序。用户确认候选项后，编辑器内将渲染出链接胶囊；点击胶囊后，页面可跳转到对应笔记详情。与此同时，后端在札记保存时会通过正则提取 Markdown 中的 `[[目标名]]`，将其同步写入 PostgreSQL 的链接索引表，并在 Neo4j 中以 Note 节点和 LINKS_TO 有向边的形式更新图拓扑。由于这一链路同时覆盖了文件正文、关系型元数据和图关系，因此也构成了本项目数据一致性要求最高的部分。基于这些关系，札记模块进一步提供全局知识图谱弹窗，以可视化方式展示笔记之间的知识结构。

值得补充的是，札记模块右侧还嵌入了独立的 Copilot 面板。该面板并不等同于解惑模块，而是专注于服务当前正在编辑的札记。系统通过全局状态共享编辑器实例与选区上下文，使 Copilot 能够静默读取整篇笔记或当前选中段落，并将大模型返回的 Markdown 内容以“插入到光标处”或“替换选中文本”的方式注入编辑器。该设计避免了用户在 AI 结果与编辑器之间进行低效的复制粘贴，也使智能辅助真正融入写作流。

### 3.3 解惑模块详细设计

解惑模块的核心是会话化 AI 问答。系统前端将历史会话、当前消息流、左右侧边栏状态与底部输入区域组织为一个完整工作台，其中左侧负责历史会话管理，中间负责消息展示与流式输出，右侧负责引用与来源展示预留。用户在输入问题后，前端通过 `streamChat` 调用 `/api/chat/stream` 接口，后端则将当前问题、历史消息、可选图片输入及控制参数组装为请求，发送至阿里百炼兼容模型接口，并以 SSE 方式将结果流回前端。

为改善流式体验，前端并不是在收到每一个微小分片后立即触发全量重绘，而是在本地维护缓冲区与刷新节奏，尽可能以平滑、连贯的方式将文本逐步刷入界面，从而减少 Markdown 重排造成的卡顿。消息区同时挂载自动滚动锚点，使长文本输出过程中视口始终能够跟随最后一行内容下移，避免用户手动拖动滚动条。左侧历史会话区使用 PostgreSQL 中的 `chat_sessions` 与 `chat_messages` 作为持久化载体，支持新建会话、继续旧会话与删除会话。删除会话的交互近期也已从浏览器原生确认框改为与札记模块风格一致的居中确认卡片，从而保证整体界面语言的一致性。

从模型职责上看，解惑模块当前定位为 Free Chat 与学术辅助解释工具，重点在于稳定的多轮会话和高质量文本生成，而不是一开始就将复杂的证据检索、RAG 排序与出处约束全部强耦合进主链路。与此同时，项目并未放弃后续的受控问答方向。由于 PostgreSQL、pgvector、Neo4j 与札记系统已经具备基础能力，未来完全可以在当前会话层之外增加带证据卡、带来源片段的 Grounded QA 模式，实现从“可用”走向“可信”的下一阶段升级。

### 3.4 用户鉴权与个人中心设计

在鉴权系统方面，项目当前已建立相对完整的 JWT 登录方案。后端通过 `/auth/send-code`、`/auth/register`、`/auth/login`、`/auth/reset-password`、`/auth/me` 与 `/auth/profile` 等接口完成邮箱验证码发送、注册、登录、密码重置、当前用户查询与资料更新。密码存储采用哈希方式而非明文入库，验证码具备有效期控制，邮箱发送则通过 SMTP 进行。前端在路由层面对不同模块实施了差异化访问策略：文库模块保持开放访问，札记与解惑在未登录状态下会被优雅拦截，并通过认证卡片引导用户进入登录页面。这一设计既保留了文库作为公共入口的开放性，又保证了涉及个人知识资产与历史对话的模块具备基本的用户隔离能力。

登录页在视觉设计上并未停留在传统表单框水平，而是通过宣纸质感背景、暖金与暖灰色彩系统、液态玻璃感表单卡片以及品牌化 Logo 区域营造出具有文化辨识度的入口体验。虽然这一部分属于前端视觉工作，但其本质仍服务于系统级设计目标，即在用户正式进入知识工作流之前建立统一的产品语气和身份感。

### 3.5 关键数据结构与接口设计

从数据库层面看，文库主数据围绕 `works`、`work_blocks`、`work_annotations`、`work_translations`、`work_appreciations` 与 embeddings 等表组织；札记相关数据围绕 `notes`、`note_links`、`note_work_refs` 与 `folders` 等元数据组织；问答相关数据围绕 `chat_sessions`、`chat_messages` 以及问答日志组织；用户系统则围绕 `users` 表展开。尽管札记正文当前已迁移到本地 Vault，但数据库元数据依旧承担着路径索引、更新时间排序、工作引用与关系同步等不可替代的作用。因此，不能简单地将当前系统理解为“完全不需要数据库的本地笔记工具”，而应理解为“本地正文真源与数据库元数据协同”的复合模式。若用于正式文档提交，建议在本节补充一张 ER 图与一张 API 分层图，以使表结构与服务边界更易于评审理解。

从接口设计上看，系统对外暴露的主要能力可归纳为四类。第一类是文库接口，包括 `/api/works`、`/api/works/{item_id}`、`/api/search` 与 `/api/related/{item_id}`；第二类是札记接口，包括 `/api/notes`、`/api/notes/tree`、`/api/notes/{note_id}`、`/api/folders` 与 `/api/notes/graph`；第三类是问答与聊天接口，包括 `/api/chat/stream`、`/api/chat/sessions` 及消息读取接口；第四类是鉴权接口，即 `/api/auth/*` 路由组。统一的接口前缀与清晰的职责边界，使前端在联调阶段能够围绕稳定契约进行快速迭代，也降低了页面层与后端实现细节之间的耦合度。

## 第四章 测试报告

### 4.1 测试环境与测试方法

本项目的测试工作主要在本地联调环境中完成，运行环境由 Docker Compose 拉起 PostgreSQL、Neo4j、Redis 与后端服务，前端则通过 Next.js 开发服务器运行。数据库方面，PostgreSQL 采用 `5433` 端口映射，Neo4j 提供 `7474` 与 `7687` 端口，Redis 采用默认 `6379` 端口，后端服务对外暴露 `8000` 端口，前端通常运行于 `3000` 端口。测试方法以接口联调测试、页面交互测试、数据一致性测试和局部回归测试为主，尚未开展完整的高并发压力测试与正式渗透测试。换言之，当前测试结论主要服务于“功能可落地、交互可使用、数据基本一致”的工程目标，而非工业级生产可用性认证。

在测试组织上，项目经历了大量以问题驱动的迭代回归过程。例如，在文库模块中，测试重点集中在主卡渲染、详情弹窗、搜索结果、关联探索、收藏、加入札记与语义检索结果可解释性；在札记模块中，测试重点集中在本地文件生成、文件树同步、双向链接跳转、图谱显示、行内重命名、自动保存、导出与 Copilot 内容注入；在解惑模块中，测试重点集中在流式输出、历史会话恢复、删除确认、滚动追踪与 Markdown 渲染稳定性；在用户系统中，则重点测试了验证码发送、注册登录、特殊测试账号覆盖规则以及登录状态保护效果。建议在正式提交时，于本章补充“典型测试用例表”与若干关键界面截图，以使测试结论更具证据性。

### 4.2 功能测试结果

从当前联调结果来看，文库模块已能够稳定完成作品加载、关键词与语义联合检索、搜索结果切换、作品详情阅读、关联作品展示、收藏与转札记等核心流程。尤其是在文库卡片与详情弹窗方面，经过多轮响应式与交互修正，当前版本已经避免了原先静态样板、点击区域过大、原生内部字段暴露以及小屏幕顶部截断等明显问题。札记模块则已从简单数据库笔记系统演进为本地 Vault 驱动的 Markdown 工作台，能够在 Web 中新建、编辑、删除笔记，并在文件系统中真实生成和更新 `.md` 文件；双向链接候选联想、胶囊渲染、跳转与图谱构建亦已打通。解惑模块能够完成流式对话、历史会话存储和删除，并在界面层实现了较为自然的打字输出体验与历史记录区管理。鉴权模块则已实现登录、注册、验证码发送、忘记密码与个人资料更新等关键能力。

需要说明的是，测试中也暴露过若干具有代表性的复杂问题，例如前端热更新缓存导致的组件路径读取错误、本地文件与 Web 状态同步的时序不一致、语义检索结果解释性不足、札记内容刷新后选中态丢失以及高分屏与 1K 屏之间的版式割裂等。上述问题已在迭代中逐步修复，但它们也说明本项目不是简单的静态展示，而是在多模块、多状态、多存储协同条件下持续进行工程收敛。因此，当前测试结论应理解为“项目已经达到稳定演示与持续开发的阶段性成熟度”，而非所有边界条件均已穷尽。

### 4.3 数据一致性与本地优先机制验证

札记模块的 Local-First 机制是测试重点中的重点。围绕这一机制，当前已验证的关键路径包括：在 Web 端新建札记后，本地 Vault 中能够生成对应 Markdown 文件；在 Web 中修改标题与正文后，本地文件与 PostgreSQL 元数据同步变化；在本地直接新增、删除或修改 Markdown 文件后，前端刷新可重新扫描目录并更新文件树；在笔记正文中写入 `[[双向链接]]` 后，PostgreSQL 链接索引与 Neo4j 图谱关系能够同步更新。虽然这一机制在设计上已具备较强可用性，但从工程角度出发，未来仍建议补充文件冲突场景、异常中断恢复场景以及并发写入场景的专项测试，以增强其健壮性论证。

### 4.4 已知局限与后续测试建议

当前版本仍存在若干值得在后续继续验证和打磨的方面。首先，文库模块的语义检索与图谱重排虽然已经具备可用性，但在复杂自然语言查询、模糊主题召回与跨作者意象挖掘方面仍有进一步优化空间；其次，札记 Copilot 虽已能够读取上下文并生成 Markdown 内容，但其注入策略、输出质量稳定性与错误反馈机制仍应继续增强；再次，解惑模块当前以 Free Chat 为主，对于严格证据约束的学术问答仍需等待 Grounded QA 体系完善；最后，用户系统虽然能够完成基础鉴权，但在正式多用户部署场景下，还需要围绕数据隔离、配额控制、文件系统权限边界和异常恢复机制进行更系统的测试。建议在后续版本中补充接口压力测试、长会话流式稳定性测试、异常断连恢复测试与安全专项测试。

## 第五章 安装及使用

### 5.1 环境准备

为正确运行本项目，部署环境至少应具备 Docker、Docker Compose、Node.js 与 Python 运行能力。项目根目录下通过 `.env` 文件统一管理数据库、图数据库、Redis、JWT、SMTP 与阿里百炼模型相关配置，因此在首次部署前，必须确认 PostgreSQL、Neo4j 与 Redis 的用户名、密码和库名设置正确，同时填写 Qwen、GLM、Embedding 与 OCR 所需的 API Key。由于本项目默认将 PostgreSQL 映射到宿主机 `5433` 端口，因此在本地连接数据库时应避免误用 `5432`。此外，若需要使用邮箱验证码功能，还需为 SMTP 母体账号提供可用的服务器地址、授权码与发件人配置。

### 5.2 启动方式

项目推荐采用容器化方式启动后端基础设施与 API 服务。在项目根目录执行如下命令后，PostgreSQL、Neo4j、Redis 与 FastAPI 后端将一并启动：

```bash
docker compose up -d
```

前端可在 `frontend` 目录下通过 Next.js 开发模式启动：

```bash
cd frontend
npm install
npm run dev
```

若环境配置无误，前端默认可通过 `http://localhost:3000` 访问，后端 API 默认可通过 `http://localhost:8000` 提供服务。后端启动时会自动初始化数据库模式，并扫描 `workspace/vault` 下的本地 Markdown 文件，确保札记系统与本地文件真源保持同步。若部署到服务器环境，应保证 `workspace` 目录具备持久化存储能力，以避免容器重建后本地札记内容丢失。

### 5.3 使用流程

普通访客进入系统后，可直接访问文库模块，围绕作品标题、作者、朝代、意象或自然语言问题进行搜索，并查看作品详情、关联推荐与收藏内容。若用户希望进入札记或解惑模块，则需要先完成登录。登录成功后，用户可以在文库中将感兴趣的作品一键转入札记，随后在札记模块继续编辑 Markdown、建立双向链接、查看知识图谱并调用 Copilot 进行润色或重写；若需要围绕某一主题进行延展式提问，则可进入解惑模块发起多轮对话，并通过会话历史持续回访既往讨论内容。对于教师、助教或比赛评审而言，该使用流程能够清晰展示系统如何从“文本获取”推进到“知识组织”再推进到“智能理解”，也即文心阁最核心的产品闭环。

### 5.4 建议补充材料

若本说明文档用于比赛终稿、课程设计答辩或论文附录，建议在本章补充部署截图、环境变量示意表、Docker 容器运行状态截图以及本地 Vault 目录示意图。这样不仅可以增强安装说明的可复现性，也有助于评审直接理解“本地 Markdown 真源”这一架构亮点如何在实际运行中落地。

## 第六章 项目总结

### 6.1 研发成果总结

从当前完成度看，文心阁已经超越了“比赛原型”常见的静态展示阶段，初步形成了一套具有真实数据、真实存储、真实交互与真实智能能力的研究型平台。文库模块已从写死样板转向数据库驱动，并在检索、详情、收藏、关联与语义解释方面建立了完整主链路；札记模块已从普通数据库笔记系统升级为本地优先的 Markdown 工作台，并通过双向链接与知识图谱实现知识网络化组织；解惑模块已具备流式输出、会话持久化和相对稳定的智能交互体验；鉴权系统则让“开放文库、私有札记与个性化问答”这种产品边界真正具备了可执行的用户层结构。换言之，文心阁当前版本最重要的价值，并不只是“功能多”，而是各功能之间的关系已经开始形成稳定的系统性。

### 6.2 项目亮点与关键难点

本项目最突出的亮点在于，其没有选择一种最容易实现、却也最容易沦为空壳的路线。它并没有停留在“做一个会显示诗词的页面、做一个会聊天的侧栏、做一个会编辑的文本框”这种拼接式原型上，而是围绕文科研究场景，构建了以 canonical schema 为基础的数据层，以 Local-First 为特征的札记层，以 Neo4j 为支撑的知识关系层，以及以阿里百炼兼容模型为驱动的智能层。这种设计使得系统从一开始就具备了向更高层级演进的可能性，例如带证据的学术问答、图谱增强型推荐、基于本地工作区的长期知识管理等。

与亮点相伴的，是多重工程难点。首先，多源异构数据统一建模本身就是一个复杂问题，任何字段漂移都可能导致前后端接口混乱。其次，本地文件系统与 Web 编辑器之间的协同远比单纯数据库更新更复杂，因为一旦将 Markdown 文件确立为真源，就必须处理刷新、扫描、外部修改、重命名、路径安全与图谱重建等连锁问题。再次，双向链接与图数据库同步要求正文、索引与拓扑三者之间保持相对一致，这对后端服务设计提出了较高要求。最后，项目还要在学术气质与现代交互之间寻找平衡，使系统既不沦为冰冷后台，也不走向与研究场景脱节的过度炫技。这些困难的存在，恰恰说明项目并非低成本拼装，而是在真实工程约束下逐步收敛而成。

### 6.3 后续展望

展望下一阶段，文心阁仍有较为明确的演进方向。其一，可继续提升文库模块的混合检索质量，将关键词、向量相似度与图谱关系进一步融合为更稳定的 GraphRAG 式检索与推荐体系。其二，可将解惑模块从 Free Chat 升级为带引用片段和证据卡片的 Grounded QA，使回答具备更强的可追溯性与学术可信度。其三，可进一步扩展札记 Local-First 生态，使之兼容更多本地目录操作、批量导入、主题模板和工作区同步能力。其四，可围绕多用户部署场景完善权限隔离、资源配额、日志追踪和数据备份方案，从而使系统具备从比赛项目走向真实服务的基础。就当前而言，文心阁已经完成了最艰难的第一阶段，即把产品逻辑、数据逻辑和交互逻辑真正焊接在一起；未来若继续迭代，其成长空间仍然相当可观。
