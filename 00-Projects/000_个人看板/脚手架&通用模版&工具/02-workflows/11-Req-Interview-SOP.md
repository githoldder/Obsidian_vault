# 需求访谈、对齐与 To B 开发通用 SOP (11-Req-Interview-SOP)

> **核心原则**：以定稿的需求规格说明书为基线，以业务为中心，拒绝“为了技术而技术”，优先满足核心业务流程，只记录增量，防止需求膨胀。

---

## 一、需求访谈与对齐 SOP

本规范适用于对接业务方（使用者）、管理层（决策方）、技术方（落地方）的需求访谈，通过漏斗模型实现需求对齐。

### 1.1 漏斗模型与使用规范
1. **Step 1 访谈**：标记：🆕新增 / 🔍澄清 / ✏️变更。
2. **Step 2 整理**：按模块归类，写明影响范围。
3. **Step 3 输出**：编号连续的清单文件。
4. **编号连续**：每次需求对齐从上一份最大编号+1开始。
5. **基线不动**：需求规格说明书不修改，变更只记录在清单中。
6. **状态标记**：✅已确认 / ⚠️待确认 / ❌已否决。

### 1.2 需求变更输出模板
```markdown
# 第 N 次需求对齐清单

> 基线文档：《软件需求规格说明书》v1.0
> 访谈日期：YYYY-MM-DD
> 参与人：XXX

## 需求变更汇总

| # | 类型 | 模块 | 需求点 | 基线原描述 | 本次确认 | 影响范围 | 状态 |
|---|------|------|--------|-----------|---------|---------|------|
| 1 | 🆕新增 | | | 无 | | | ✅已确认 |
| 2 | 🔍澄清 | | | | | | ✅已确认 |
| 3 | ✏️变更 | | | | | | ⚠️待确认 |

## 待确认项
- [ ] ...

## 里程碑约束
- 目标交付日期：
- 阻塞项：
```

## 二、To B App 开发通用阶段规范

To B 应用程序（如政务信息化小程序、企业管理系统）的通用生命周期六阶段：

### 阶段1：需求调研与规划（做什么、为谁做、解决什么问题）
- **需求清单**：划分核心需求（P0 必须实现，如订单录入、数据查询）与非核心需求（P1 二期迭代，如报表可视化、智能提醒）。
- **系统目标**：量化指标（如“订单处理效率提升50%”）。
- **范围界定**：明确做什么、不做什么，避免需求无限膨胀。

### 阶段2：系统设计（怎么做，技术落地的蓝图）
- **业务设计**：
  - 梳理业务流程：绘制核心流程图，标注节点职责、数据流转方向。
  - 功能模块拆分：按业务拆分独立模块。
  - 定义核心实体：确定关键数据对象及属性。
- **技术设计**：
  - 架构选型：小型系统用单体架构；中大型系统用微服务架构；数据密集型用数仓/分布式。
  - 技术栈：根据业务规模匹配前端（uni-app/Vue3/React+TS）、后端（Java/Go/Python/Node.js）、数据库（MySQL+Redis）。
  - 数据库设计：按三范式设计表，使用 ER 图表示，并优化索引。
  - 接口设计：Swagger/OpenAPI 标准化定义接口，采用 RESTful 风格。

### 阶段3：开发实现（保证代码可维护、功能符合需求）
- **开发规范**：统一风格、注释，使用 Git 版本控制。
- **开发流程**：先开发核心 P0 模块，再开发非核心模块。边做边测。
- **解耦原则**：高内聚、低耦合，单个模块功能聚焦，模块间依赖尽可能少。

### 阶段4：测试验证（找出所有 BUG，确保可用稳定）
- **测试分级**：
  1. **单元测试**：测试单个函数、接口，确保最小功能单元无 BUG。
  2. **集成测试**：测试模块间的交互，确保组合后正常工作。
  3. **系统测试**：模拟真实业务场景，测试功能、性能、兼容性。
  4. **验收测试（UAT）**：业务方亲自测试，符合需求并出具《验收报告》后才可上线。
- **非功能测试**：对中大型系统进行性能压测、安全测试、兼容性测试。

### 阶段5：部署上线（环境隔离，平稳上线）
- **环境分级**：开发环境 (dev) -> 测试环境 (test) -> 预生产环境 (pre) -> 生产环境 (prod)。
- **部署方式**：单节点使用 Docker Compose，多节点使用 Docker+K8s/K3s 编排。
- **上线流程**：预生产验证 -> 生产部署（灰度发布或全量上线） -> 监控状态。

### 阶段6：运维与迭代（稳定运行，持续优化）
- **日常运维**：使用 Prometheus/Grafana 监控 CPU、内存、磁盘和接口响应；定期备份数据库。
- **系统优化**：针对运行中的问题（如慢查询、高并发限制）做索引和架构优化。
- **迭代循环**：基于用户反馈进入下一轮“需求-设计-开发-测试-上线”循环。

## 三、Vibe Coding 工作流（AI 时代独立团队/单人开发思路）

### 3.1 模式选择
- **文档主导模式**：适用于需求已基本明确的大项目。
- **原型/MVP 先行模式**：适用于需求模糊的 idea 阶段，快速完成可行性验证。若原型对话复杂度膨胀，则立即停止，通过 AI 阅读代码生成功能文档，并强制切换到文档主导模式。

### 3.2 协作六步骤
1. **发散需求（Layer 1 需求对接）**：
   - 提示词：“我现在在设计一个 xx 系统，功能描述如下：【功能草案】，请帮我：1. 调研类似系统 2. 扩充和细化功能。不涉及技术内容。”
2. **PRD 编写与原子化拆解**：
   - 编写包含术语表、交互方式和验收标准的 `PRD.md`。
   - 将细分功能拆成最小可执行原子化任务存入 `PRD.json`。完成一个功能标记为 `true`。
3. **Plan + Review（Layer 2 全栈开发）**：
   - 一个 AI 制定 plan，另一个 AI 交叉 Review 提出建议，持续两轮以上，人工确认后实施。
4. **实现**：
   - 使用 Git 进行分支和 commit 管理，按模块开发自测。
5. **功能测试与迭代（Layer 3 测试维护）**：
   - 提示词：“针对刚才的所有修改设计测试，确保简洁、可维护、只 cover 关键逻辑、关注交界点而非实现细节。”
6. **人工 Review**：
   - 对比分支与 main 变动，审核无误后合并。
