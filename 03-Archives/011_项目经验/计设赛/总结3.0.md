### 当前存在的缺点

1. **无导出能力**：赛道要求提交《练习测试及学生反馈》等结构化数字资源，目前没有一键导出 PDF/Word 的功能。
2. **单端设计**：目前只有学生端，缺少教师端（查看全班统计、批量点评、管理课件库等）。
3. **数据种类有限**：当前数据库只有唐诗宋词，缺少更丰富的文学作品（如元曲、散文等）。
4. **离线能力弱**：所有 AI 功能依赖网络调用（n8n → DeepSeek），断网后只有本地兜底的简单回复。
5. **前端打磨不足**：部分模块的 UI 交互还需进一步打磨（如答题卡动画、导图渲染效果等）。

## 可创新的方向

1. **知识图谱可视化探索**：让学生在前端直接浏览 Neo4j 中的诗人→作品→意象关系网络，点击节点跳转到相关诗词，实现"图谱漫游式学习"。

2. **多轮对话记忆**：当前每次问答是独立的，可以引入 Redis 或数据库保存对话历史，让 AI 能够记住"你刚才问了什么"，实现连续追问（如"那李白呢？"→ 自动关联上下文）。

3. **自适应学习路径**：根据学生的错题模式和学习行为统计，自动推荐下一首应该学习的诗词（如"你在'借景抒情'类题目上正确率较低，建议学习《登高》"）。

4. **朗诵 + 跟读评测**：接入 TTS 生成标准朗诵音频，再接入 ASR 让学生跟读，对比语音评分，增加多模态互动。

5. **教师端仪表盘**：开发教师视角，展示全班学习数据统计（热力图、错题分布、学习时长排行），支持批量生成点评并一键导出。

6. **竞赛答题模式**：加入限时答题、积分排行榜等游戏化元素，提高学生学习积极性。

## 为什么 n8n 响应这么慢？

n8n 响应慢的原因是**多层网络调用的累积延迟**：

### 调用链路分析

```
前端 → Go 后端 → n8n Webhook → DeepSeek API → n8n → Go 后端 → 前端
```

每一步的延迟：

| 环节                  | 耗时估算      | 原因                                |
| ------------------- | --------- | --------------------------------- |
| 前端 → Go 后端          | ~50ms     | 本地 Docker 网络，很快                   |
| Go 后端 → n8n Webhook | ~100ms    | Docker 内部网络通信                     |
| n8n 工作流执行           | ~500ms-2s | n8n 需要解析节点、加载 Skills 文件、拼装 Prompt |
| n8n → DeepSeek API  | **3-20s** | **最大瓶颈！** DeepSeek 大模型推理延迟        |
| n8n → Go 后端返回       | ~100ms    | 返程通信                              |
| **总计**              | **4-25s** | 主要被 LLM 推理阻塞                      |

### 核心瓶颈

1. **DeepSeek API 推理延迟**：大模型生成长文本（如阶梯三道题 + 解析）需要 5-20 秒，这是所有 LLM 应用的共同瓶颈，无法简单优化。
2. **n8n 中间层开销**：n8n 作为工作流引擎，每次请求都要遍历节点、执行 JavaScript 表达式、HTTP 转发等，增加了 0.5-2 秒的额外开销。
3. **缺少流式输出**：当前架构不支持 SSE/WebSocket 流式输出，用户必须等整个响应生成完毕才能看到结果。

### 优化建议

| 方案 | 效果 | 难度 |
|------|------|------|
| **绕过 n8n 直连 DeepSeek**（当前已支持 `DEEPSEEK_API_KEY` 直连模式） | 减少 0.5-2s 中间层延迟 | 低（已实现 fallback） |
| **流式输出（SSE）** | 用户秒出第一个字，体验大幅提升 | 中 |
| **结果缓存**（相同诗词+页面的请求直接返回缓存） | 重复请求秒回 | 低 |
| **异步预生成**（翻页时后台预生成下一页的内容） | 用户感知延迟降为 0 | 中 |
