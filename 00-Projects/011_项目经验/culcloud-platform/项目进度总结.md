## 2️⃣ PM2 vs Docker Compose 技术搭配

这是**架构决策问题**，也是你答辩会被追着问的点。先说清楚设计，再写代码：

### 正确分工

code复制

```
┌──────────────────────────────────────┐
│ PM2 (本地演示) │
│ ┌─────────┐ ┌──────────────┐ │
│ │ Flask │ │ React (Vite)│ │
│ │ 分析API │ │ 前端 │ │
│ └─────────┘ └──────────────┘ │
├──────────────────────────────────────┤
│ Docker Compose (集群服务) │
│ ┌──────┐ ┌──────┐ ┌──────────┐ │
│ │Redis │ │MinIO│ │Gotenberg │ │
│ └──────┘ └──────┘ └──────────┘ │
│ ┌──────┐ ┌──────────┐ │
│ │Spark │ │FastAPI │ │
│ │(on HDFS)│后端 │ │
│ └──────┘ └──────────┘ │
└──────────────────────────────────────┘
```

### 决策逻辑

|场景|用|理由|
|---|---|---|
|**有状态的基础设施**（Redis, MinIO, DB）|Docker Compose|状态管理、网络隔离、重启策略|
|**计算密集型**（Spark, Hadoop）|Docker Compose|资源隔离、依赖管理、集群扩展|
|**演示专用前端**（React Dev Server）|PM2|热重载、开发体验好|
|**演示专用轻量 API**（Flask 分析层）|PM2|方便改代码、热重启|

### 你为什么选 PM2 + Docker Compose 混搭的答辩理由（直接背）：

> “我的数据层（Redis、MinIO、对象存储）和计算层（Spark）是有状态的、需要严格资源隔离的，所以用 Docker Compose 管理——它们不会在演示过程中被改动。而前端和 Flask 分析 API 是演示迭代中频繁修改的，PM2 能让它们热重载，不需要每改一行代码就 rebuild 镜像。架构上这是**分层治理**：基础设施层用容器化保证一致性，应用层用进程管理器保证迭代效率。”

### 如果老师追问「为什么不全部 Docker Compose」：

> “全 Docker Compose 当然可以，但演示场景下每次改前端 CSS 都要等 build 和 restart，浪费交互时间。PM2 + Docker Compose 是**开发演示混合模式**，生产环境会全部统一到 Docker Compose + K8s。”

**这个逻辑够硬，老师能听懂而且会认可**。

## 3️⃣ 分布式集群服务状态可视化

你的方案很好：「点击刷新 → 触发脚本 → 获取集群状态日志 → 展现在大屏」。下面给出**具体实现路径**：

### 方案设计

code复制

```
用户点击「刷新集群状态」按钮
 ↓
前端发 POST /api/analytics/cluster/refresh
 ↓
Flask API 执行脚本：
 ┌─────────────────────────────┐
 │ 1. subprocess: `docker stats --no-stream` → 容器级CPU/内存 │
 │ 2. Redis PING → 缓存状态 │
 │ 3. 检查各端口是否监听 │
 │ 4. (可选) SSH到hadoop容器: `hdfs dfsadmin -report` │
 │ 5. 汇总JSON返回 │
 └─────────────────────────────┘
 ↓
前端 ECharts 更新仪表盘（5 秒刷新 + 手动刷新双模式）
```

### 可视化内容

|卡片|数据来源|图表类型|
|---|---|---|
|服务健康状态|端口探测 + Docker inspect|红绿灯指示卡（全绿/部分异常）|
|容器资源占用|`docker stats`|环形进度条（CPU/内存）|
|HDFS 数据节点状态|`hdfs dfsadmin -report`|节点列表 + 健康状态|
|Redis 缓存命中率|Redis INFO|实时折线|
|最近系统事件|系统日志|滚动列表|

### 实现要点

1. **`POST /api/analytics/cluster/refresh`**：返回的是「快照」而非流数据
2. **`GET /api/analytics/cluster/status`**：返回最近的快照缓存
3. **超时兜底**：某个服务挂了 → 不阻塞整个刷新，返回 partial 数据 + 状态标记

**这个功能对你答辩特别加分**——不仅展示了数据可视化，还展示了**系统运维思维**，老师最喜欢问"怎么知道系统在正常跑"。

## 4️⃣ 老师很较真——你需要掌握什么

好在你面对的是一个好老师。他追着问，反而是让你真学到东西。我列个**答辩题库**，你按这个准备：

### 容器化与编排

- **Docker Compose 的 `depends_on` 和 `healthcheck` 有什么区别？**  
    → `depends_on` 控制启动顺序，`healthcheck` 确保服务真正就绪
- **网络模式 `bridge` vs `host` 你在哪用了？为什么？**  
    → `bridge` 隔离性好容易扩展，`host` 只在需要高吞吐的场景
- **如果 Redis 容器挂了，你的系统怎么处理？**  
    → Flask API 有 try-except，返回空数据+error标记，前端显示"服务异常"状态
- **`profiles` 是什么？**  
    → `--profile analytics` 是选择性启动，不是所有用户都需要 Spark

### 数据分析管道

- **为什么用 Redis 做任务队列？跟 RabbitMQ / Kafka 比呢？**  
    → Redis 轻量，这个场景不需要消息持久化和消费者组，选最简单的
- **MinIO 和 HDFS 有什么区别？你为什么要同时用？**  
    → 不同场景：MinIO（S3 兼容，上传文件存储）vs HDFS（大数据分析，如部署 MapReduce 作业用 HDFS），二者并不冲突。当前架构中文件处理用 MinIO，未来大数据分析可对接 HDFS
- **Spark local[*] 和 yarn 模式区别？**  
    → `local[*]` 是单机多线程，适合你的降级方案；生产用 YARN 是集群作业调度

### 系统设计

- **前端刷新 F5 和点击刷新按钮，数据一致性怎么保证？**  
    → F5 刷的是整个页面，点击刷新只发 API 请求，页面状态不丢失
- **你的大屏数据是实时？准实时？还是离线？**  
    → 默认模式：从 `data/spark-output/` 读离线分析结果（秒级返回）。点击刷新时直接查 Redis/MinIO（实时但不保证性能）。**分清楚谁说**
- **如果用户上传了 1000 个文件，你的系统会怎么样？**  
    → MinIO 扛得住（对象存储设计就是海量），Redis 会内存压力变大——所以需要 `SCAN` 而不是 `KEYS *`

### Spark 专项

- **数据倾斜怎么办？** → `repartition()` 重新分片
- **Spark 为什么比 MapReduce 快？** → 内存计算 + DAG 调度 + 基于 RDD 的延迟计算
