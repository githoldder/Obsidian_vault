# 接口隔离原则（ISP / Interface Segregation Principle）

## 📖 定义-解释-示例

### ISP 的经典定义

> **客户端不应该被迫依赖它不使用的方法。**
> —— Robert C. Martin

另一等价表述：**多个专用接口优于一个庞大的通用接口。** 如果你有一个 50 个方法的巨型接口，而实现类只需要其中 3 个——它被迫实现其余 47 个空方法或抛异常。这就是 ISP 要解决的问题。

### ISP 的核心洞察

问题的根源在于"胖接口"（Fat Interface）。当一个接口过于臃肿时，它把多个不同客户端的关注点强行绑定在同一个契约中。结果：
- 实现类被污染：需要实现大量不相关的方法
- 客户端被耦合：修改接口的任何一个方法（即使本人不用）都会影响所有实现类
- 编译重编译：接口变了 → 所有实现类都要重新编译

### 违背 ISP 的典型案例

**胖接口**：

```java
interface Worker {
    void work();
    void eat();
    void sleep();
}
```

看起来合理——"工人需要工作、吃饭、睡觉"。问题来了：

```java
class HumanWorker implements Worker {
    public void work() { /* 正常工作 */ }
    public void eat() { /* 吃饭休息 */ }
    public void sleep() { /* 回家睡觉 */ }
}

class RobotWorker implements Worker {
    public void work() { /* 24小时运转 */ }
    public void eat() { 
        throw new UnsupportedOperationException("机器人不吃东西！");
    }
    public void sleep() {
        throw new UnsupportedOperationException("机器人不睡觉！");
    }
}
```

`RobotWorker` 被迫实现 `eat()` 和 `sleep()`——这两个方法对它没有任何意义。每次看到 `RobotWorker` 的代码，你都要承受这两个"僵尸方法"的认知负担。`Worker` 接口太胖——它把"工作能力"和"生物需求"两个不同的关注点合并在了一起。

**ISP 修复**：

```java
interface Workable {
    void work();
}

interface Eatable {
    void eat();
}

interface Sleepable {
    void sleep();
}

class HumanWorker implements Workable, Eatable, Sleepable {
    public void work() { ... }
    public void eat() { ... }
    public void sleep() { ... }
}

class RobotWorker implements Workable {
    public void work() { ... }  // 只需要实现这一个！
}
```

现在每个接口只有与其名称相关的方法。`RobotWorker` 只实现它需要的。干净利落。

### ISP 与 LSP 的关系

LSP 说"子类应该能替换父类"，ISP 是 LSP 在接口层面的体现。当接口太胖，实现类被迫用空实现抛异常 → 这个实现类无法安全地替换为同样接口的其他使用场景 → 既违背 ISP，也间接违背 LSP。

### ISP 与单一职责原则（SRP）

两者在精神上一致但粒度不同：
- **SRP** 作用于**类**层面："一个类只负责一件事"
- **ISP** 作用于**接口**层面："一个接口只为一个客户端服务"

SRP 指导你把一个上帝类拆成几个小类；ISP 指导你把一个上帝接口拆成几个小接口。配合使用，类小而专，接口精而准。

### ISP 的实践判断标准

**何时说明你的接口太胖了？**
1. 实现类中有空方法或 `throw new UnsupportedOperationException()` → 这是 ISP 违背的明显证据
2. 不同的调用者只使用接口中的不同子集 → 说明这个接口实际上服务于多个不同的客户端
3. 某个方法只在特定实现中需要，但被放在了公共接口上 → 应该抽离为单独的接口
4. 修改接口的一个方法，却影响到了大量的实现类 → 耦合面太大

**接口的粒度应该多细？**
没有绝对的答案，但有一条实用规则：**一个接口应该服务于一组紧密相关的客户端**。如果客户端 A 和 B 需要的功能 80% 相同，它们在同一个接口上；如果它们只有 20% 重叠，应该分两个接口。这是判断的标尺。

### ISP 在现实中的体现

Java 标准库中就有优秀的 ISP 实践：
- `java.io.Closeable` 只包含一个 `close()` 方法——任何需要关闭的资源都实现它，无需担心其他不相关的操作
- `java.lang.Runnable` 只有一个 `run()`——线程只需实现这一个方法
- `java.util.Comparator` 只有一个 `compare()`——排序只需一个比较逻辑

这些极简接口之所以强大，正是因为它们只做一件事，但把这件事做成了全 Java 生态的公约数。

**反例**：现实中的老旧 ORM 框架，`Repository<T>` 接口包含 40+ 个方法（CRUD、分页、排序、批量、流式、事件、回调……），然后所有 `UserRepository`、`OrderRepository` 都不得不实现全部。后来好的框架开始按关注点拆分：`ReadRepository`、`WriteRepository`、`PagingRepository`。

### ISP 不仅仅是接口数量

ISP 更深层的含义是：**你的公开 API 就是一份契约**。契约太多条 → 维护者疲于应付 → 调用者困惑害怕 → 系统僵化。小而专注的接口让：
- 实现者轻松（只需实现关心的几个方法）
- 调用者清晰（我只依赖我真正需要的）
- 系统灵活（新增行为 = 新增接口 + 让需要的类实现，不影响已有类）
