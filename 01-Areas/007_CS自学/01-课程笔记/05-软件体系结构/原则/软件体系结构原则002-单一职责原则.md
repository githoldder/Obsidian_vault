# 单一职责原则（SRP / Single Responsibility Principle）

## 📖 定义-解释-示例

### SRP 的经典定义

> **一个类应该有且仅有一个引起变化的原因。**
> —— Robert C. Martin（Uncle Bob）

换句话说：一个类只负责一件事。如果某个类承担了多个不同的职责，那么任何一个职责的变化都可能影响该类。当你修改代码时一不小心搞崩了不相干的功能，这就是 SRP 违背的信号。

### 深入理解："职责"是什么？

"职责"不是"一个方法只做一件事"（那个粒度太小了），而是**"一个类只为某一个业务参与者（Actor）服务"**。

不同的业务参与者有不同的需求和变更节奏：
- **财务部**关心的是工资计算规则
- **人力资源部**关心的是工时统计规则
- 如果 `Employee` 类同时包含 `calculatePay()` 和 `reportHours()`，它就同时为财务部和人力资源部服务
- 当财务部要求改工资计算逻辑时，你动了这个类 → 变更是为财务部做的 → 但可能引入 bug 影响人力资源部的功能

这就是"单一职责"的核心洞察：**职责 = 对某一类业务参与者的责任**。解耦不同参与者关心的逻辑，是为了让它们可以独立演化。

### 违背 SRP 的典型案例

一个反模式——"上帝类"（God Class）：

```java
class Employee {
    // 薪资计算 —— 为 CFO 服务
    public double calculatePay() { ... }
    
    // 工时报表 —— 为 COO 服务
    public String reportHours() { ... }
    
    // 员工数据持久化 —— 为 CTO 服务
    public void save() { ... }
    
    // 发送邮件通知
    public void sendNotification() { ... }
}
```

这个类同时耦合了业务逻辑、数据持久化、通知发送。任何一个需求变化都需要修改这个类，所有关注点都耦合在一起。

**重构后**：

```java
class Employee {  // 纯数据 + 核心行为
    private String name;
    private double baseSalary;
    // getters / setters
}

class PayCalculator {    // 薪资计算逻辑
    public double calculatePay(Employee e) { ... }
}

class HoursReporter {    // 工时报表逻辑
    public String reportHours(Employee e) { ... }
}

class EmployeeRepository {  // 持久化
    public void save(Employee e) { ... }
}

class NotificationService {  // 通知
    public void sendNotification(String msg) { ... }
}
```

现在，每个类只有一个变化的原因：`PayCalculator` 只因为薪资规则变化而修改，`HoursReporter` 只因为报表格式变化而修改。

### SRP 的价值

**1. 变更隔离**
当薪资计算规则改变时，只需要修改 `PayCalculator`。`HoursReporter` 和 `EmployeeRepository` 完全不受影响。变更的范围 = 文件修改的个数 = 出 bug 的可能范围。

**2. 可测试性**
单一职责的类更容易编写单元测试。测试 `PayCalculator` 不需要 mock 数据库，测试 `HoursReporter` 不需要 mock 邮件服务。

**3. 可复用性**
当 `PayCalculator` 只做薪资计算且做得好时，其他模块可以放心地重用它。反之，`Employee` 上帝类被不同模块依赖时，谁都不敢随便改。

**4. 可读性**
`PayCalculator` 这个名字本身就告诉读者它做什么。而 `Employee` 上帝类需要翻遍几百行代码才能理解它的所有责任。

### 如何识别 SRP 的违背？

问自己三个问题：
1. **这个类有多个"if 业务场景 A do X else do Y"的分支吗？** → 可能是不同职责塞进了同一个类
2. **修改某个需求时，总得动这个类且担心搞坏其他功能？** → SRP 违背的红色警报
3. **描述这个类的行为时用了"和"字？** → "这个类计算薪资**和**生成报表**和**保存数据" → 三种职责，应该三个类

### SRP 的边界——不要过度拆分

SRP 并不意味着一个类只有一个方法。正确的粒度：**一个类为一个明确的参与者服务**。100 个类每个只有 3 行，不如 10 个类每个 30 行。关键不是"少"，而是"独立演化"。

过度拆分的信号：类之间的耦合反而更大了，修改一个功能要同时打开 5 个文件。这违背了高内聚的原则。**SRP 是为了高内聚，不是为了拆分而拆分。**

### SRP 与其他 SOLID 原则的关系

- **开闭原则（OCP）** 是 SRP 的自然延伸：每个类只做一件事 → 扩展这件事的行为时，不用修改已有的其他职责
- 违背 SRP 的类几乎一定违背**接口隔离原则（ISP）**：上帝类需要大而全的接口
- SRP 是 SOLID 的第一原则，也是最基础、影响最深远的——代码混乱的源头往往就是职责不清
