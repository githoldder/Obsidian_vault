# 人机高密度通信协议（Context Engineering）

> 高效的人机沟通，不是把 Prompt 写得更漂亮，而是把人的认知状态压缩成机器可执行的规格，同时尽量减少模型需要猜测的东西。

---

## 定义

**人机高密度通信协议**，是关于如何用最少的交互成本，把人的意图、上下文、约束、判断标准与期望结果，高保真地传递给大模型，并尽可能减少歧义、遗漏和来回修正的一套方法框架。它回答的是一个长期困扰所有 AI 使用者的根本问题：**在人—AI 的语言接口中，怎样才能"一次说清"，而不是反复修正？**

这个问题的背景，是 Prompt Engineering 正在发生一次范式迁移。过去，人们把精力花在"如何措辞"上，追求写出一句"更漂亮"的提示词。但现在，Anthropic 已明确把重点从 prompt engineering 推向 context engineering，研究的重心从"寻找正确措辞"转向"配置最有可能产生目标行为的整个 Context State"。这意味着，Prompt 的价值不再来自语言技巧，而来自信息架构。

用一句话概括这个框架的核心判断：**高质量 Prompt 不是文采，而是信息压缩。** 真正高效的人，不是"Prompt 写得漂亮的人"，而是"会组织 Context、会减少模型猜测的人"。

## 解释

要理解这套框架，首先要看它如何诊断"沟通为什么低效"。人机沟通的损耗，并不发生在输入输出两端，而发生在中间环节。整条链路可以被拆解为：意图（Intent）→ 已知信息（Context）与隐含信息（Assumption）→ 语言表达（Language）→ 模型解析 → 模型内部推理 → 输出（Output）→ 人类判断是否满意 → 不满意则重新描述。

这里的关键洞察是：人脑里一句"帮我重新设计这个系统，要企业级、论文能用、架构严谨、能持续迭代"，一旦被压缩成"帮我设计一个系统架构图"，信息损失是巨大的。于是，人机语言交互的核心问题，就可以被抽象为：**如何最大化单位 Token 所携带的"可执行信息量"。**

基于这个判断，一条 Prompt 可以被抽象成七个变量的叠加，记作 **P = I + C + S + K + E + O + V**。其中 I 是 Intent（我到底要什么），C 是 Context（为什么要做），S 是 Scope（做到哪里），K 是 Constraints（什么不能做），E 是 Evaluation（什么叫做好），O 是 Output（最终交付什么），V 是 Verification（如何检查）。大多数人的 Prompt 只有 I，其余六个变量全靠模型去猜，于是模型只能给出一个"看似正确、实则泛泛"的答案。

但更重要的是第二个发现：**不要把所有信息都塞进 Prompt。** 传统 Prompt Engineering 问的是"怎么写一句更好的 Prompt"，而 Context Engineering 问的是"模型在做决定时，究竟应该看到哪些信息"。这两者的差别，是把问题从"措辞"上升到"上下文状态配置"——包括当前任务、已知事实、历史决策、约束、示例、工具和外部资料。

那么，什么信息最值得传递？这里可以建立一个"信息密度金字塔"。从金字塔顶到底，信息价值递减：Evaluation（什么叫成功）→ Output（我要什么形式）→ Constraints（什么不能发生）→ Scope（做到什么程度）→ Context（为什么要做）→ Intent（我要解决什么）→ Raw Information（你需要知道什么）。其中最容易被普通用户遗漏的，恰恰是位于塔顶的 **Evaluation——"什么叫做好"**。

同样是"帮我设计一个数据库"，一句高质量的 Prompt 会补上：优先级（一致性 > 可扩展性 > 查询性能）、需要支持的功能（元数据、目录树、权限、版本管理）、重点分析维度（数据模型、索引、事务边界、分库分表路径）、明确排除项（不讨论前端），以及最终交付物（ER 模型 + 核心表设计 + 关键索引 + 架构演进方案）。这种 Prompt 的信息量并非来自"更长"，而是来自**更少的无效文字 + 更多的决策信息**。

## 七个核心能力

在筛掉大量互相重复的技巧之后，真正留下来的只有七个核心能力。

**第一，Intent（目标）。** 要明确"我要解决什么问题"，而不是模糊地说"介绍一下微服务"。真正有效的表述是："我正在设计一个中型 SaaS 系统，需要判断微服务是否值得采用，请从团队规模、部署复杂度、故障隔离、数据一致性、开发效率五个维度评价。"

**第二，Context（背景）。** 不要让对方猜。一句"这是本科毕业设计"，其信息价值远高于"这是一个系统"，因为它瞬间锁定了方案的复杂度上限和评判尺度。

**第三，Constraint（边界）。** 优秀 Prompt 会大量使用"不讨论 / 不需要 / 不允许 / 必须"。因为**排除搜索空间，比增加搜索空间更有效**——一句"不讨论 Kubernetes"，就删掉了一大片可能产生的答案空间。

**第四，Example（示例）。** 这是各家官方文档高度一致的结论：few-shot 示例往往比抽象描述更强。与其写"请采用专业、简洁、结构化的方式回答"，不如直接给一个"问题—回答"的格式范本，然后说"按上述结构解释 Kafka"。**示例本质上是"可执行规格"。**

**第五，Contrast（正反对比）。** 告诉 AI"什么是错的"。比如"不要把'高并发'直接等同于'必须微服务'，应该先分析具体负载、瓶颈和故障边界再判断"。这相当于提供了 Positive Example + Negative Example，比一句"请严谨一些"有效得多。

**第六，Output Contract（输出协议）。** 明确规定输出结构和字段，甚至直接给出 JSON Schema（conclusion / risks / recommendation / confidence）。这已经非常接近 API Contract。

**第七，Verification（验证）。** 让 AI 在输出后自查：是否遗漏硬约束、是否引入了未提供的假设、是否存在内部矛盾、是否满足输出格式。注意，这比单纯让 AI"认真思考"更有价值。

## 应用：三个等级与九项协议

理解了七个核心能力之后，日常沟通可以被分成三个等级。

**Level 1 是自然语言**，比如"帮我看看这个架构"，适合简单任务。**Level 2 是结构化 Prompt**，即"目标 + 背景 + 重点 + 输出格式"，适合专业工作。**Level 3 是交互式 Specification**，它不仅给出目标、已有事实、假设、当前决策、待解决问题、约束和评价标准，还明确要求 AI"找出冲突、找出遗漏、提出候选方案、给出推荐、等我确认后继续"。到了这一层，它已经不再是一条 Prompt，而是一份 **Human-AI Working Protocol**。

如果要把整个研究压缩成一个可直接使用的协议，就是下面这九项：

```
[GOAL]        我要解决什么？
[CONTEXT]     你需要知道什么？
[INPUT]       我给你的原始材料是什么？
[SCOPE]       你负责什么，不负责什么？
[CONSTRAINTS] 必须满足什么？禁止什么？
[CRITERIA]    什么叫做好？
[REFERENCE]   什么样的结果是我认可的？
[OUTPUT]      最终交付什么？
[VERIFY]      完成后检查什么？
```

但需要注意一个关键点：**不是每次聊天都必须写满这九项。** 真正高手的特点，恰恰是"只显式提供那些模型无法可靠推断的信息"。

## 问题与答案

**问：为什么我按照 Prompt 技巧清单写了，效果还是不好？**

答：因为技巧清单往往把注意力引向"措辞"层面，而忽略了信息架构层面。一条 Prompt 效果差，通常不是因为缺少某个"魔法词汇"，而是因为缺少了六个变量中的一个或多个——尤其是 Evaluation（什么叫做好）和 Constraints（什么不能做）。当模型需要猜测"做到什么程度算好""什么绝对不能发生"时，它只能给出一个保守而泛泛的答案。改进的方向不是加更多形容词，而是补全缺失的决策信息。

**问："把 Prompt 写长一点"是不是就等于高密度？**

答：不是。高密度 Prompt 的衡量标准是"信息密度 × 可解释性 × 可执行性"，而不是字数。一个冗长但充满无效文字（寒暄、重复、模糊形容）的 Prompt，信息密度反而更低。真正的高密度，是"更少的无效文字 + 更多的决策信息"。一个有用的判据是：如果你删掉一句话之后，模型的行为不会发生变化，那么这句话就是冗余的。

**问：Context Engineering 和 Prompt Engineering 到底有什么区别？**

答：Prompt Engineering 问的是"怎么写一句更好的提示词"，它把焦点放在单条指令的措辞上；Context Engineering 问的是"模型在做决定时应该看到哪些信息"，它把焦点放在整个上下文状态（任务、事实、历史、约束、示例、工具、外部资料）的配置上。前者是战术，后者是架构。Anthropic 已经明确把重心从前者推向后者，这标志着这个领域从"语言技巧"走向"信息架构"。

**问：那套"终极模板"适合所有场景吗？**

答：适合复杂任务，不适合简单任务。对于"帮我看看这个架构"这类简单请求，套用完整模板反而是一种过度工程。终极模板的价值，在于当你面对一个多目标、多约束、需要反复修正的复杂任务时，它能一次性把意图、背景、事实、假设、约束、关注点、判断标准和输出协议全部交代清楚，从而把"多轮返工"压缩成"一次说清"。真正的判断力，在于知道什么时候该显式，什么时候该省略。

**问：2026 年这个方向有什么值得关注的新趋势？**

答：最值得关注的是"AI 帮人把问题问好"这一反向研究。传统模式是 Human → Prompt → AI → Answer；未来模式可能是 Human → Intent → Specification → Context Engineering → AI → Verification → Human。2026 年 8 月出现的一篇论文《Asking Questions the Right Way》提出一个多 Agent 系统，不直接回答用户，而是先通过对话补全 Prompt 的结构化要素。在一个探索性实验（N=4）中，结构完整度从 42% 提升到 91%，达到满意所需的轮次明显下降；但样本太小，只能作为早期证据。

## 总结

人机高密度通信协议之所以值得长期维护，是因为它不只是一堆 Prompt 技巧，而是在逼近一个更大的问题：**Human-AI Specification / Human-AI Communication Protocol**。

它与你之前在探索的 Spec-Driven Development / AI-Native 工作流，其实是同一个问题的不同层次：Spec-Driven Development 解决的是"人 → AI → 软件"的信息传递，而这里讨论的是更底层的"人 → AI"的信息传递。换句话说，这条线可能最终会变成整个人机协作方法论的最底层一层。

如果只记住一句话，那就是：**高效的人机沟通，不是"把 Prompt 写得更漂亮"，而是把人的认知状态压缩成机器可执行的规格，同时尽量减少模型需要猜测的东西。**

用公式表达就是：

> 通信效率 ≈（意图 + 背景 + 约束 + 判断标准）／（歧义 + 缺失信息 + 冗余）
